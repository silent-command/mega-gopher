# MEGA65 Gopher Client — Requirements

> **Platform knowledge lives in [PLATFORM-NOTES.md](PLATFORM-NOTES.md).**
> That file collects the MEGA65/llvm-mos findings from this project in a
> project-independent form — runtime environment, memory map, DMA hazards,
> the second stack's integration, debugging techniques and dead ends — and is the
> thing to read first when starting another MEGA65 project. This document
> keeps the gopher-specific design decisions and the full narrative of how
> each finding was reached.

## 1. Goal

A native MEGA65 program that browses Gopherspace (RFC 1436): connect to a
gopher server, display its menu, follow links, and read text files — running
directly on MEGA65 hardware (or Xemu) over the built-in 100Mbit Ethernet
controller.

## 2. Decisions already made

| Question | Decision |
|---|---|
| Networking foundation | ~~the first stack~~ **Superseded** — switched to the second stack after the phase-1 spike confirmed the first stack's DNS path is broken (see R-1 history below) and found the second stack to be a more actively-maintained, protocol-correctness-focused 65CE02 assembly TCP/IP stack with working DNS. It runs as a standalone binary in bank 4 (not linked into our program), called via a documented `SYS`-style jump-table ABI. **No LICENSE file exists upstream** — fine for local hardware development, but needs resolving with the upstream author before any public release of the gopher client. |
| Display mode | Native 80-column MEGA65/C65 text mode. Gopher menu lines (up to ~70 chars of display text per RFC 1436) fit without wrapping. |
| v1 feature scope | Menus (item type `1`), text files (item type `0`), and search (item type `7`, added 2026-08-30 — see 2.6). No downloads, no images. |
| Toolchain | CC65 (matches the first stack's reference code). |
| Primary test server | ~~`gopher.floodgap.com`~~ **Superseded** — floodgap now rate-limits us after the many connections made while debugging R-8, and its own menu asks clients not to cost it bandwidth (R-8c). Default target is now `gopherpedia.com`, with `tools/test_gopher_server.py` on the LAN as the controlled-experiment server. |
| **Run mode (FR-0a)** | **Must run in native MEGA65 mode, not GO64/C64 mode.** Added 2026-08-30 at the user's request. Not satisfied by the current build: `cl65 -t c64` emits a `$0801` load address with a C64 BASIC stub (`SYS 2061`), so it requires GO64 today. the second stack is *not* the constraint — its jump table is designed around BASIC 65's `SYS` with 24-bit linear addresses, which is a native-mode feature, and its own example apps (terminal, IRC) run natively. This forces a toolchain change; see §2.1. |
| **Distribution (FR-0b)** | **Must ship as a single `.d81` disk image** containing the program and every supporting file. Added 2026-08-30 at the user's request. Blocked today by *how* the second stack's `eth.bin` and the trampoline are obtained: `src/gopher_boot.c` reads them with hyppo fileio, which reads the SD card's **FAT** filesystem, while a mounted `.d81` is reached through **CBM DOS** instead — so files inside a `.d81` are invisible to that code path. Fix is to stop depending on FAT: embed the payloads in the binary (started — `src/eth_payload.c`, generated by `tools/gen_payload.py`), or load them through CBM DOS. Embedding also removes the risk of the three files drifting out of sync. |

## 2.1 Toolchain evaluation for native MEGA65 mode (FR-0a)

CC65 cannot produce a native-mode MEGA65 program: it has no MEGA65 target,
and `mega65-libc` ships no linker config for one. FR-0a therefore forces a
toolchain change. Both candidates are **already installed on this machine**
and both were smoke-tested on 2026-08-30.

| | llvm-mos | Calypsi 5.18 |
|---|---|---|
| Location | `~/llvm-mos` (`mos-mega65-clang`) | `/usr/local/bin/{cc6502,ln6502}` |
| MEGA65 target | `mos-platform/mega65` + examples | `--target MEGA65` |
| CPU | generic 6502 | **`--core 45gs02`** (the real MEGA65 CPU) |
| Native `$2001` PRG | **verified** — built an 80-byte PRG, load address `$2001` | configs target `$2001`; link needs `--output-format` (default output is ELF) |
| `mega65-libc` support | **yes** — 38 `__clang__` conditionals vs 14 `__CC65__` | **no** — zero Calypsi references; platform layer would need porting |
| Banking past 64KB | not evident | **`mega65-banked.scm`**: `bank1` `$10000-$1ffff`, `bank45` `$40000-$5ffff` as `far` data |
| String literal encoding | standard C | **`--string-literals ENCODING`** |
| Licensing | open source | proprietary, free non-commercial tier |

**Why the `bank45` line matters**: `$40000-$5ffff` is exactly where the second stack
(`$42000`) and its receive ring (bank 5) live. Calypsi can address that
range as qualified `far` data directly, which could remove most of the
`trampoline.asm` + the far-call header machinery we hand-built because CC65 cannot
emit a `MAP` far call. Whether the linker can also *place* `eth.bin` into
bank 4 at load time (which would satisfy FR-0b with no runtime copy at all)
is promising but **unverified** — worth testing before relying on it.

**Why `--string-literals` matters**: CC65 silently rewrites string literals
into PETSCII at compile time. That single behaviour has now caused four
separate bugs here — R-5, R-6, the title bar, and `open("TRAMP.BIN")`
failing to match its FAT directory entry. Being able to state the encoding
removes the whole class.

**Assessment.** Both satisfy FR-0a. Neither is meaningfully better for
FR-0b, which is really about dropping the FAT dependency (embed the
payloads) rather than about the compiler.

- **llvm-mos is the lower-risk port**: `mega65-libc` already supports it, so
  `lpeek`/`lpoke`/`lcopy`/`mega65_io_enable` and all of conio come along
  unchanged — that is the single largest body of code we would otherwise
  rewrite. Open source, and its native `$2001` output is verified working.
- **Calypsi is the higher-ceiling option**: real 45GS02 codegen, genuine
  banking to escape the ~64KB ceiling noted in §4, direct `far` access to
  banks 4/5, and explicit string-literal encoding. The cost is porting the
  platform layer and a proprietary dependency, which compounds the existing
  unresolved licensing question around the second stack having no LICENSE file.

**Recommendation**: attempt llvm-mos first, since it preserves `mega65-libc`
and is verified to produce a native `$2001` binary. Keep Calypsi as the
fallback if llvm-mos's MEGA65 platform turns out to lack what we need for
the bank-4 far calls. Either way, re-validate on hardware the three things
that were only ever tested under CC65/C64 mode: the `MAP` trampoline, the
`$0334` trampoline placement (C64 tape buffer — may not be free under BASIC
65), and `mega65_io_enable()`/screen setup.

## 2.2 llvm-mos port — WORKING (2026-08-30)

FR-0a and FR-0b are both met. Build with `./build-native.sh`; the
deliverable is `bin/GOPHER.D81`, containing a single self-contained
`gopher` PRG with the second stack and the trampoline embedded.

**Verified end-to-end on hardware, in native MEGA65 mode:**
DHCP -> DNS (`gopherpedia.com`) -> TCP connect -> request -> 5635-byte
receive -> parse -> 64-item menu with `[DIR]` links, ASCII-art banner,
selection highlight -> follow-link navigation to a new 53-item menu.
Load address `$2001`, ~34KB, no `m65 -@` injection and no SD-card files.

**Five bugs the port exposed.** Each was found by border-colour bisection
on hardware, and all but the first were latent assumptions that only C64
mode had been hiding.

1. **`ETH_WAIT_100MS` never returns** (the second stack; patched locally). It spun
   until `$D012` changed, which never happens in native mode, so
   `ETH_INIT` -- which calls it 42 times to give the PHY 4 seconds --
   hung forever. Now paces on the `$D7FA` frame counter, verified to tick
   in native mode both normally and under `sei`. Same flaw as R-1c.
2. **Screen relocation.** `setscreenaddr(0x51000)` existed only to dodge
   the C64-mode collision at `$0801`. Native programs load at `$2001`, so
   it fought the ROM's VIC-IV setup and produced repeating garbage. Now
   `#ifdef __CC65__`.
3. **String-literal encoding.** CC65 rewrites literals to screen codes at
   compile time; llvm-mos leaves them ASCII. Symptom: uppercase perfect,
   lowercase garbage. Fixed structurally -- text is now plain ASCII
   throughout and translated once at draw time -- which also removes the
   literals-vs-network asymmetry behind R-5, R-6 and the title bar.
4. **`cputsxy()` crashes** under llvm-mos here. `gopher_putsxy()` now uses
   `gotoxy()` + `cputs()`. This one was expensive to find: the client used
   cursor-based output early and positioned output only later, so the
   crash surfaced far from its cause.
5. **`sprintf()` with `%s` crashes.** `clrscr()`, `sayln()` and
   `newline()` all completed and the next statement died, scribbling the
   VIC-IV registers on the way down -- so it presented as a display fault,
   not a string bug. All `%s` uses are now `strcpy`/`strcat`; `%u` is
   unaffected and still used.

**Interrupts.** `trampoline.asm` brackets the mapped window in `sei` and
deliberately does **not** re-enable them on return: while mapped, CPU
`$2000-$7FFF` is bank 4, so any IRQ handler living there would execute
the second stack's bytes. C64 mode survived this by luck (its handler is in ROM at
`$EA31`, outside the window). Leaving them off is safe here because every
loop polls hardware directly (`$D7FA`, `$D610`). An earlier note in this
section claimed a `cli` on return was *fatal* and that `ETH_INIT` left an
interrupt asserted; that diagnosis was wrong -- the hangs it was based on
were bugs 1, 4 and 5. Whether a `cli` would now be safe has not been
re-tested, and there is no reason to.

**CC65 build removed** (2026-08-30, at the user's direction). llvm-mos is
now the only toolchain: `src/` holds just the client, `gopher_screen.c` has
a single output path, and `build-native.sh` is the only build. The CC65-era
hardware probes are archived under `attic/cc65-diagnostics/` rather than
deleted, because the R-1c/R-5/R-6/R-8 findings in this document cite them
as evidence; they no longer build, and their README says why.

**Two client bugs found while verifying the remaining UI paths:**

- **Unbounded receive loop.** `fetch_menu`/`fetch_text` spun forever if a
  server accepted the connection and then sent nothing — which is exactly
  what a rate-limiting server does. It presented as a hang on a freshly
  cleared screen, indistinguishable from a crash. Both loops now give up
  after `IDLE_FRAMES_LIMIT` (500 frames, ~10s) with no new bytes, and parse
  whatever did arrive: a truncated menu beats a dead client.
- **Stale cursor after `clrscr()`.** `clrscr()` does not reliably home the
  cursor here, so `sayln()` output landed wherever the previous screen left
  it — the first line of a text file appeared in the bottom-right corner
  with the rest running off-screen. Both fetch paths now `gotoxy(0, 0)`
  explicitly.

**UI verified on hardware** (native mode, loaded from the mounted .d81 with
`LOAD"GOPHER",8` + `RUN`): Up/Down move the selection and correctly skip
non-selectable info lines; Return follows a link; Stop returns to the
previous menu; Home returns to the start page; and a type-0 text file
fetches and renders from the top. Text paging is still phase 6 — long files
scroll off rather than paginate.

**Both known limitations closed (2026-08-30):**

- **Text paging (FR-9/10/11) implemented.** Text files are now buffered
  into a new banked line store (`src/gopher_text.c`, bank 5 `$5a000`,
  250 lines x 80-byte fixed records so "show line N" is one multiply)
  and paged: Up/Down scroll a line, Return pages, Home jumps to the top,
  Stop returns to the menu, and a status line shows `Lines a-b of n`
  (plus `(truncated)` at the 250-line cap). Buffering first also closes
  the connection before the user starts reading rather than holding it
  open while they linger. Verified on hardware with a 60-line file:
  1-23 -> 24-46 on Return, then 27-49 after three Downs.
- **Over-long menu lines clipped.** A marker plus a full-length display
  string can reach the right edge of an 80-column row, wrapping onto the
  next row and overwriting the item drawn there; rows are now clipped to
  79 columns. Verified with a deliberately over-long info line.

**A third bug surfaced while testing the pager**: the receive loops broke
out the moment the peer closed the connection, discarding bytes still
sitting in the second stack's receive ring. A 60-line text file arrived as 31
lines. Both loops now keep draining after closure until a whole frame
yields nothing. This had been silently truncating responses whenever a
server sent everything and closed immediately — worth remembering as a
general shape: *connection closed* is not *all data seen*.

**`HOME_HOST`/`HOME_PORT`/`HOME_SELECTOR` are now build-time overridable**
(`-DHOME_HOST='"192.168.1.232"' -DHOME_PORT=7070`) so a LAN test build
needs no source edit. During the port the checked-in default was briefly
pointed at a local Mac, which would have been a poor thing to ship;
`build-native.sh` takes the public default and the shipping binary is
checked for the LAN address before release.

**Text-file corruption — ROOT-CAUSED AND FIXED: a zero-length DMA copies
64KB.** Reported by the user after following a link from gopherpedia's
front page: screen corrupted, client unresponsive.

**Cause**: `cputs()`/`cputsxy()` in mega65-libc do
`lcopy(src, dst, strlen(s))` and `lfill(colour, strlen(s))`. For an empty
string that length is 0, and `lcopy()` passes the count straight to
DMAgic (`dmalist.count = count`) with no zero check — and DMAgic treats a
count of 0 as **65536**. So drawing one blank line fires a 64KB DMA over
memory. Real articles are full of blank lines; menu rows always start with
a non-empty `[DIR] `-style marker, which is exactly why menus were never
affected. **Fix**: `gopher_puts()`/`gopher_putsxy()` return early on an
empty string.

**How it was found.** Reproduced deterministically by replaying a
byte-exact capture of a real article
(`tools/fixtures/gopherpedia-article.txt` via
`tools/text_item_server.py`) — the invented fixtures never reproduced it,
because none of them contained a blank line. Then bisected on hardware:

| what runs | result |
| --- | --- |
| receive, store nothing | clean |
| receive + store all 129 lines | clean |
| + `text_get_line()` read-back, no drawing | clean |
| + `gopher_putsxy()` on each line | **corrupts** |

Five plausible theories were tested and disproved first, each by a
hardware run: bank-5 overlap (the VIC-IV screen pointer was measured at
`$00000800`, nowhere near the stores), byte content (sanitising the 41
tabs and the UTF-8 did not help), line length (clamping to 40 did not
help), record/copy size, and signed pointer casts. The decisive clue came
from the disabled-rendering build: four *literal* lines drew fine while
article lines did not — the difference being that articles contain empty
strings.

**Worth remembering**: any `lcopy`/`lfill` reachable with a
caller-controlled length needs a zero guard on this hardware. The same
latent hazard exists in mega65-libc's own `cputsxy()`, which is a
candidate upstream report.

**Not a regression from paging.** The previous streaming implementation
drew the same blank lines through the same `cputs()` path, so text viewing
was broken before the pager existed; it had simply never been exercised
against a real article, because gopherpedia refused every type-0 fetch
attempted earlier.

**Text store moved to attic RAM — the 250-line truncation is gone.**
A text file is now held in expansion RAM at `$8000000` (4000 lines), with
the old bank-5 tail (250 lines) kept as a fallback. Verified on hardware
with a 516-line article: all 516 lines stored and paged, no truncation.

Two memory facts were measured rather than assumed, and the first
overturned the obvious plan:

- **Banks 2 and 3 are NOT free.** `$20000-$3ffff` is the 128KB C65 ROM: a
  readback probe wrote a pattern every 1KB across both banks and 126 of
  128 samples failed to stick. The tempting "just move the store to the
  unused banks 2-3" would have failed silently.
- **Attic RAM is present and reliable** on this machine (128 samples, zero
  mismatches). It is optional hardware, so `text_init()` probes it at
  startup by readback and falls back to bank 5 if absent, rather than
  assuming every MEGA65 has it.

Remaining bank-5 free space is only ~8.6KB (`$51000-$51fff` plus the tail
above the text store), which is why attic RAM rather than rearranging
bank 5 was the right answer.

**Colours are now inherited, not imposed (FR-13).** Border (`$d020`) and
background (`$d021`) were never written by this program -- the blue was
simply what the ROM left -- so the only thing being overridden was the
text colour, which conio hard-defaults to `COLOUR_WHITE`. Startup now
reads the ROM's current-colour byte at `$0286` and uses that, and `C`
cycles the text colour in the menu (skipping the background colour so the
text cannot vanish). Persisting the choice belongs with the config file
work.

**UTF-8 folding (was: two dots per accented character).** Articles are
UTF-8, so `u-umlaut` is two bytes and the byte-wise sanitiser produced two
dots -- "M..hren". `gopher_fold_utf8()` now decodes sequences and folds a
codepoint to one displayable byte, mapping the Latin-1 letters onto their
unaccented base (so it reads "Muhren"), common punctuation onto ASCII
equivalents (curly quotes, en/em dashes, ellipsis, bullet), and anything
else to '.'. Folding happens **before storage**, so stored line lengths
match what is drawn and truncation stays honest. Applied to both text
lines and menu display text. Verified on hardware against the real
article.

**Typed URL entry (FR-1).** `G` opens a "Go to:" prompt with a small line
editor (echo, DEL to rub out, Return to accept, Stop to cancel).
`parse_url()` is deliberately lenient -- it accepts
`gopher://host:port/selector`, `host:port/selector`, `host/selector` or a
bare `host` -- because typing a URL on a C65 keyboard is punishment
enough. The visited page is pushed onto the history so Stop still walks
back. Verified on hardware.

**Bookmarks / config file — STILL DISABLED after a second attempt.**
`CONFIG_DISK_ENABLED` is 0. The code is complete and compiles; it does not
work inside the client.

**What now works** (verified, keep these):

- The KERNAL environment switch. `kernal_env` restores `$01 = $3f`,
  `$d030 = $64` and enables interrupts -- exactly what llvm-mos's own
  `.fini.990` teardown restores -- then puts the original state back.
- The call shape. Small helper wrappers passing pointers through `"r"`
  constraints destabilised the machine; the identical sequence written
  inline in one function does not. `gopher_kernal.c` is deliberately
  written as two flat functions for that reason.
- Clearing `$91` (STOP flag) and `$c6` before each operation. Once
  interrupts are on, the KERNAL keyboard scan runs and a stale STOP
  reading aborts any I/O call -- the visible symptom was BASIC printing
  `BREAK` repeatedly.
- Standalone probes using all of the above **did** write a file and read a
  non-existent one cleanly, confirmed by downloading the .d81 and finding
  `probe.txt` in its directory.

**What still fails**: with all of that in the real client, `GOPHER.CFG` is
never written (confirmed by downloading the image twice) and the display
ends up black. So something about the client's state -- the VIC-IV
80-column setup, the second stack resident in banks 4/5, a 37KB program -- is
incompatible with the KERNAL environment in a way a small probe does not
reproduce. Two crashes and several dead ends went into establishing that.

**Raw SD sector route also tried, also not working yet.** The idea was
to skip the KERNAL entirely using `mega65_sdcard_readsector()` /
`writesector()`, which need no interrupts, no `$d030` switch and no ROM
banking. Measured on hardware:

- `mega65_sdcard_open()` then `mega65_sdcard_readsector(0)` returns
  success (0) and the buffer does get 266 non-zero bytes, so something is
  happening.
- But it is **not** the MBR: the boot signature at offset 510/511 reads
  `00 00` rather than `55 aa`, and the first bytes
  (`00 ff 44 bb a0 a0 c0 00`) do not look like a partition sector.

So the card needs initialisation beyond `mega65_sdcard_open()` (which only
calls `mega65_sdcard_reset()`), and there may be a conflict with the
hypervisor already having the card open for the mounted .d81. A FAT32 walk
built on this returned garbage geometry, as expected given the underlying
reads.

**Status: #4 is parked.** Three distinct approaches have now been tried
(KERNAL/CBM DOS, KERNAL with a corrected machine environment, raw SD
sectors), each hitting a different platform-integration problem, and the
client is complete and useful without it. Everything learned is recorded
above so none of it has to be rediscovered.

**If picked up again**, the two most promising leads are: work out the
correct SD initialisation sequence (compare against how `mega65_ftp`'s
on-device helper or the MEGA65 ROM does it, rather than guessing), or ask
upstream whether mega65-libc will expose a write path in its hyppo fileio,
which would make a loose SD-card config file trivial and sidestep the .d81
entirely.

**Environmental note**: `gopherpedia.com` began refusing connections
partway through this work after many rapid retries, exactly as floodgap
did (R-8c). It recovered on its own. When public servers start refusing,
test against `tools/test_gopher_server.py` on the LAN -- the client now
accepts a dotted-quad host and skips DNS entirely (FR-2).

## 2.3 Deferred ideas (not yet implemented)

**Colour hotkeys (requested 2026-08-30).** Rename `C:Colour` to
`F:Foreground` and add matching keys for background and border. All three
are already inheritable at startup and conio exposes `bordercolor()` and
`bgcolor()` alongside `textcolor()`, so this is mostly UI: three keys, and
a guard so foreground never lands on the current background (the existing
`C` handler already skips that case, and the same care is needed for the
background key so text does not vanish behind it).

**Saving to disk, with a user-chosen destination (requested 2026-08-31).**
When saving is added -- an article from the pager first, binary downloads
(item type `9`) later -- the user must be able to choose where it goes.
The MEGA65 offers up to two mounted drives (a disk image, plus either a
second image or the real 3.5" floppy) and the SD card itself.

*The three destinations are not one feature.* Drives 8 and 9 are CBM DOS
devices reachable through the KERNAL path we already have; the SD card is
not a CBM DOS device at all. That splits the work:

- **Drives 8 and 9 — cheap.** `kernal_write_file()` already issues
  `SETLFS` with the device hardcoded as `ldx #8`
  (`src/gopher_kernal.c:63`). Supporting drive 9 is that one value.
  Caveat: `gopher_kernal.c`'s own comment records that passing values
  through `"r"` constraints *across function boundaries* destabilised the
  machine, so the device number must be loaded from a local inside the
  existing single function -- not threaded in via a new helper.
- **SD card — a separate subsystem.** Not reachable via CBM DOS.
  mega65-libc's fileio can *read* FAT but is read-only, so writing needs
  hypervisor calls or a FAT32 writer. This is its own project, not a third
  entry on the same code path.

Other things this requires:

- **Probe before offering.** Drive 9 may be an absent floppy or an unmounted
  second slot. Offer only destinations that answer (KERNAL sets ST bit 7,
  `$80`, for DEVICE NOT PRESENT) rather than letting the user pick a dead
  device and get a cryptic failure.
- **Saving to the disk we booted from.** If `GOPHER.D81` is on device 8,
  saving there makes the distribution image double as the scratch disk.
  It works, but prefer drive 9 when present, and handle a write-protected
  image cleanly.
- **Filenames differ per destination.** CBM DOS is 16 characters of
  PETSCII with `: , = * ?` excluded; FAT32 is not. Gopher selectors need
  sanitising and collision handling, and the rules are not the same for
  both targets.
- **The screen-teardown problem is orthogonal and still gates all of
  this.** See 2.2 and `gopher_config.c`: the KERNAL write works standalone
  but destabilised the machine when integrated, because `$d030` carries
  VIC-III/IV configuration as well as ROM banking and fights the
  80-column screen. A save is discrete and user-initiated, so it can
  deliberately tear the screen down and rebuild it afterwards -- a shape
  config persistence could never use. Untested.

Suggested order: prove the write path with "save this article" to device 8
(the text is already buffered in attic RAM, so it needs no new network
code), then add the 8/9 chooser, then binary downloads, then the SD card.

**Quit to BASIC 65 — ATTEMPTED, NOT WORKING.** Returning from `main()`
does reach BASIC: the runtime's `__after_main` runs `.fini.990` (restoring
`$01 = $3f`, `$d030 = $64`, `cli`) then `rts`es back to whatever ran the
program. "Goodbye." appears and BASIC is demonstrably alive and printing.

**But BASIC is unusable afterwards**: every line typed at the READY prompt
comes back as `break` and never executes, so the colour-then-rerun
workflow this was meant to enable does not work. Four cleanup attempts on
exit, none of which helped:

| attempt | result |
| --- | --- |
| `$91 = $ff` (STOP flag), `$c6 = 0`, single `$d610` poke | still `break` |
| drain `$d610` in a loop (each write advances one key) | more `break`s |
| also `$dc00 = $ff` (deselect keyboard rows) | still `break` |
| screen left as-is vs cleared | no difference |

The screen also comes back black until BASIC next redraws, because
`.fini.990` changes `$d030`, which carries VIC-III/IV configuration.

**Reset-as-quit is not an option**: measured directly -- after `m65 -F`,
`LOAD"GOPHER",8` returns `62, FILE NOT FOUND`. Device 8 answers, so the
drive is there, but **the mounted .d81 does not survive a reset**. Quitting
via the reset vector would strand the user with no way to re-run without
re-mounting.

`gopher_tcp_disconnect()` was added for this and is worth keeping -- a
clean TCP close on the way out is right regardless.

**Consequence**: the `C:Colour` key stays, since the plan to replace it
with quit-then-set-colours-in-BASIC does not currently work. Startup
colour inheritance still works, so setting colours in BASIC *before*
running is already effective.

**If picked up again**: the remaining unknown is what state BASIC's editor
is actually reacting to. Worth reading the MEGA65 KERNAL's STOP/keyboard
handling to find what it reads, rather than guessing at locations as above.
A BASIC *warm start* jump (rather than `rts` or a full reset) may also
reinitialise the editor while leaving the mount intact -- untested.

**RESOLVED (2026-09-05, version 0.3): Q and RUN/STOP at the start screen
leave for BASIC.** Found while giving mega-ftp the same feature (its
REQUIREMENTS.md 5.7). Two facts settle the old questions. First, on this
llvm-mos runtime `exit()` is `jsr fini; bra .` (disassembled from
`libcrt0.a`; the serial monitor showed the CPU parked on that branch),
so returning from `main()` never reaches BASIC at all; whatever printed
"Goodbye." above was an older runtime. Second, the "break" after every
line was BASIC running on a zero page the program had overwritten: the
C program's zero-page sections sit at `$02-$8F`, on top of BASIC's own
variables, and no keyboard poke repairs that.

The way out is the KERNAL's reset entry, reached by software:
`src/gopher_exit.S` holds the 45E100 in reset, drains the keyboard
queue, copies a 20-byte stub to `$1FB0` (spare low RAM) and jumps to
it; the stub clears the MAP, restores `$01` and `$D030` to the values
`.fini` uses, and jumps through `($FFFC)`. The ROM re-initialises the
screen editor, the DOS and BASIC's zero page as at power-on, and Hyppo
does not run, so the mounted disk survives. Measured: banner and
`READY.`, `PRINT 2+2` answers `4`, `RUN "GOPHER"` starts the client
with no `MOUNT`; the same from Q inside a menu.

Two things learned on the way. The stub must run from outside
`$2000-$BFFF`: restoring the map in place put the BASIC ROM over the
program's own code and parked the CPU at `$908D`. And the routine has
to be assembly here: the C version (which mega-ftp uses) crashed this
program's start-up into zero page merely by being referenced, with
identical zero-page layouts in the booting and crashing builds, so it
was link-time code generation reshaping the rest of the program, the
family of fault 2.34 records. Assembly is outside its reach.

And a third, found when the final build was verified again: the exit
was first bound to RUN/STOP at the start screen, and one run of that
landed in the ROM's machine-language monitor with a fresh reset state
on its screen. The C65 ROM enters the monitor when it finds RUN/STOP
held at reset, and a reset a few milliseconds after the keypress finds
exactly that. So the start screen's quit is Q typed at its prompt, and
`gopher_exit.S` waits half a second (frame counter, interrupts still
on) after quieting the ethernet controller before it jumps, so a still
held key is released and any event the controller had in flight is
taken by the program's own handler. Verified twice on hardware after
the change, both exits.

And a fourth, reported by the user from the FTP client and shared here
(0.3.1): BASIC came back taking commands into an unreadable screen.
`conioinit()` points the font at the ROM's copy in bank 2 (`$D06A` =
2) with the VIC-IV hot registers off, so the ROM's reset never
recomputed the pointer. The screenshot tool renders screen memory
itself and could not see it; a diff of the VIC registers against a
clean boot could, and after `gopher_exit.S` sets `$D06A` to 0 and turns
the hot registers on, the registers match a clean boot in all but the
raster counters (mega-ftp REQUIREMENTS.md 5.9).

And a fifth (0.3.2), the user's report that 0.3.1 still garbled BASIC.
It did, from a menu: measured by the same register diff after browsing
a menu and a page, changing colours and pressing Q, `$D06A` was 2 again,
while the start-screen quit had measured 0. The routine was the same;
the order was wrong. It wrote the font's bank and then turned the hot
registers on, and turning them on re-derives the character-set pointer
from the classic registers, which on the menu screen put the bank back
to 2. Hot registers first now, the bank last, and once more inside the
stub as the final write before the reset vector. The browse-then-quit
diff is then empty. The 0.3.1 check had trusted the screen-memory
renderer, which is exactly the tool 5.9 of the FTP client says cannot
see this; the register diff is the only proof of the picture.

## 2.4 Startup chooser and colour keys (2026-08-30)

- **Startup site chooser** replaces going straight to a compiled-in
  default. Options are 1 (type an address), 2 (gopherpedia.com), 3
  (gopher.floodgap.com). Option 1 reuses the same `read_line()` and
  `parse_url()` as the in-app `G` key, so there is one line editor and one
  URL parser rather than two. Whatever is chosen becomes the Home target,
  so `Home` returns there instead of to a hardcoded site.
- **`F` cycles the foreground**, renamed from `C:Colour`.
- **`B` cycles background and border together**, keeping them identical so
  the screen reads as one surface. Each cycle skips the current foreground
  colour, mirroring the foreground cycle's skip of the background --
  otherwise text becomes invisible against its own background.
- **`B` no longer means bookmark.** The bookmark handler is removed and the
  key is hidden from the help line, since config persistence is disabled
  (see the config notes above). `gopher_config.c` and `gopher_kernal.c`
  remain in the tree with their findings intact.
- The startup `config_load()` call was dropped: bookmarks are disabled and
  the chooser now decides the start page, so there was nothing for it to
  override.

**DNS caching — implemented.** `gopher_dns_resolve()` now checks a small
cache before doing any work, and stores successful lookups.

Why it mattered: the resolver is called on *every* fetch, from both
`fetch_menu()` and `fetch_text()`, so moving around one site re-resolved
the same hostname each time. That is expensive here because of the R-1c
workaround -- a throwaway warm-up query, then 40 frames (~0.8s) of
waiting, then up to 250 more frames for the answer.

Design notes:

- 4 entries (hostname + 4-byte IP, ~144 bytes), round-robin replacement.
  Browsing stays within one host most of the time, so this is plenty.
- Hostnames compare **case-insensitively**: one typed by hand need not
  match the capitalisation a menu supplied.
- `gopher_dns_invalidate()` drops an entry, and both fetch paths call it
  when a connection fails. There is no clock to expire entries against, so
  a stale address that was never retried would be worse than an occasional
  extra lookup.
- A dotted-quad host still short-circuits before the cache is consulted.

Measured on hardware: following a link that previously needed ~22 seconds
completed within 12.

## 2.5 Intermittent "connection failed" — stale TCP state (fixed)

Reported by the user: frequent connection failures when following links,
including on sites that had just been browsed successfully.

**Cause**: the client never closed a connection. Gopher servers close the
connection themselves once a response is sent, leaving the second stack in
CLOSE_WAIT -- directly observed during the R-8 work, where `TCP_STATE` read
7 after a *successful* fetch. `gopher_tcp_disconnect()` existed but was
dead code, called from nowhere. So every fetch after the first issued
CONNECT_START against a socket that had never been released.

**Fix**: `gopher_tcp_connect()` now issues the stack's FORCE_CLOSED call and lets
the stack settle for a few frames before starting a new connection.
FORCE_CLOSED rather than the graceful DISCONNECT, because this is local
cleanup of a connection the peer has already finished with, and a graceful
close would add its own wait to every fetch.

**This partly invalidates earlier diagnoses.** Connection failures were
repeatedly attributed to server-side rate limiting during development
(R-8c, and several floodgap/gopherpedia failures). Rate limiting is real --
floodgap refused us outright for a stretch -- but an unknown share of those
failures was this bug. The evidence was there and misread: the multi-server
test needed an explicit FORCE_CLOSED between targets, and when that
sequencing was wrong its connects failed in exactly this way. That was
noted at the time as a quirk of the test harness rather than recognised as
a defect in the client.

**Verified**: four consecutive operations (initial fetch, follow link,
back, follow another link) with no failures. Not proof the intermittent
failures are gone -- the original symptom was intermittent -- so it needs
real browsing to confirm.

## 2.6 Search support — item type `7` (2026-08-30)

Gopher search items (type `7`) are now selectable and usable. Verified

**Protocol.** RFC 1436 sends a query by transmitting the item's selector,
a TAB, then the query text, terminated as usual by CRLF. The response is a
normal menu, so the results page needs no new rendering path — it re-enters

**Changes.**

- `gopher_items.c`: `item_is_selectable()` now accepts `GOPHER_TYPE_SEARCH`,

- `gopher.c`: the Return handler prompts `Search for: ` via the existing

## 2.7 Intermittent DNS and connection failures — root cause (2026-08-31)

The user continued to report "DNS resolution failed" and "connection
failed" on hosts that had worked seconds earlier, after the stale-TCP fix
in 2.5. That fix was real but addressed a different cause; this is the
remaining one.

**Root cause: the second stack never retransmits.** Both retry timers are driven by
the raster-based clock described in the upstream issue draft
(an issue note kept with the second stack):

- `DNS_FRAME_TICK` (`dns.asm:666`) and `CONNECT_FRAME_WRAP_TICK`
  (`eth.asm`) both detect elapsed time by testing whether the sampled
  VIC-II raster value *decreased*.
- That value does not advance on this hardware, so the comparison never
  fires, the retry counters never decrement, and neither a DNS query nor a
  SYN is ever retransmitted.
- The give-up paths are driven by the same tick, so the stack does not
  report failure either — it simply sits in `DNS_STATE_WAIT` / `SYN_SENT`
  until the client's own timeout expires.

The consequence is that **any single dropped packet is fatal to that
request**. Ordinary internet packet loss therefore produced exactly the
intermittent, unexplainable failures reported — including on hosts that
had just responded.

**Fix: retry in the client.** `gopher_dns_resolve()` and
`gopher_tcp_connect()` now perform their own retries, using the working
`$D7FA` frame clock the client already paces on:

| | attempts | per attempt | worst case |
|---|---|---|---|
| DNS | 3 | ~2s | ~6s |
| TCP connect | 3 | ~5s | ~15s |

Each DNS attempt re-issues the query (the second stack bumps its message ID and
re-sends); each connect attempt issues a fresh `CONNECT_START` after a
`FORCE_CLOSED`, which is effectively the SYN retransmission the stack owes
us. Results that are *final* are not retried: a real `DNS_STATE_FAIL`
(no such host) and an explicit `CONN_FAILED` (RST) both stop immediately,
so a genuine error is still reported quickly.

**Fix: say which failure it was.** One "ERROR: connection failed" line
covered at least five distinct causes, which made it impossible to tell a
client bug from a server being down. `gopher_net_error` now records the
reason and `say_net_error()` reports it with the host, the address
actually tried, and the number of attempts:

```
ERROR: Refused by host (nothing listening?)
  Host: 192.168.1.232
  Addr: 192.168.1.232:7099
  Tried 3 times
```

Codes: `GNERR_DNS_BUSY`, `GNERR_DNS_NOREPLY`, `GNERR_DNS_NOTFOUND`,
`GNERR_CONN_REFUSED`, `GNERR_CONN_NOREPLY`, `GNERR_SEND`.

Showing the address separates "this name resolves somewhere wrong" from
"that machine is not answering", which is most of the diagnosis.

**Verified on hardware (2026-08-31)**: bogus hostname reported
`DNS: host not found` without retrying; a closed port on the LAN reported
`Refused by host` with the address; an unroutable address reported
`No reply from host`. A 15-iteration connection soak against gopherpedia
completed with zero failures.

## 2.8 Menu parser read past the end of each line (2026-08-31)

Found while running the adversarial test server (`tools/adversarial_server.py`)
on hardware. **This is the main cause of the intermittent "connection
failed" reports**, more so than the retry problem in 2.7.

**The bug.** `fetch_menu()` called `parse_and_store_line(linebuf, linelen)`
without ever writing `linebuf[linelen] = 0`. The parser walks the buffer
with `*p` tests, and its final field -- the port -- has no trailing tab to
stop at, so the digit loop ran past the end of the current line into
whatever a previous, *longer* line had left in the reused buffer. Any
stale digits there were appended to the port:

```
real port 7072 + stale "1"   -> 5185
real port 7072 + stale "72"  -> 51912      (both observed on hardware)
```

The client then connected to that bogus port and the host refused.

**Why it looked random.** The corruption depends on the relative lengths
of adjacent menu lines, so it is deterministic per menu but appears
arbitrary to the user: most links work, a couple always fail. Replaying
the old behaviour against gopherpedia's live front page shows **2 of its
64 items** would connect to port 7070 instead of 70 --
`Psmith_in_the_City` and `Encyclopaedia_Britannica_Eleventh_Edition`.
That is exactly the reported symptom: failures on a site that was working
seconds earlier.

A line with fewer than three tabs could pick up a corrupt host or
selector by the same mechanism.

**Fix.** Terminate the buffer at both parse sites in `fetch_menu()`.
`fetch_text()` was already doing this correctly, which is why text files
never showed the problem -- only the menu path, which is where hosts and
ports come from, was affected.

**Testing note.** The 15-iteration soak in 2.7 passed because Home
re-fetches a location built by `parse_url()`, which never goes through the
item store. It therefore could not have caught this. Soaks must follow
*links* to exercise item-derived locations.

## 2.10 Menu snapshots and truncation reporting (2026-08-31)

The two items left open after the adversarial pass.

**Back no longer loses your place, or re-fetches.** History entries now
carry the cursor position (`hist_selected` / `hist_page`) and a snapshot
of the item store. `history_push()` saves them on the way in;
`history_pop()` restores them on the way out and tells the caller the
fetch can be skipped entirely.

Snapshots live in attic RAM at `$8060000`, clear of the text store
(`$8000000` + 4000 x 80 = `$804e200`), one 32,000-byte slot per history
level. `item_snapshot_init()` probes the region itself with a readback
rather than trusting the text store's probe, since it is 384KB further up;
if attic RAM is absent every snapshot call returns 0 and Back falls back
to re-fetching, so the feature degrades rather than breaks. The empty-menu
case skips the copy, because a zero-length DMA transfers 65536 bytes.

**Menus now report truncation.** `item_overflowed` is set when a menu
exceeds `MAX_ITEMS`, and the status line reads `Item 1 of 200
(truncated)` -- matching what the text pager already did. Previously the
excess was dropped silently and simply looked like a short menu.

**Cost, and how the depth was chosen.** Snapshots cost ~1KB of code, which
came out of `MAX_HISTORY` (10 -> 8; each level is a full location, ~117
bytes). That depth was set from measurement, not guesswork:

| | bytes |
|---|---|
| gap between `__bss_end` (`$cd9b`) and stack top (`$d000`) | 613 |
| deepest stack use observed on hardware | 133 |
| spare | 480 (4.6x) |

The peak was measured by painting the gap with `0xA5` at startup and
dumping it with `m65 --memsave` after nested menus, articles, search, the
pager, the 5000-line document and the error paths. The instrumentation has
since been removed.

**Verified on hardware:** cursor restored after leaving an article (item
44 of 64), after a submenu (item 17 of 64), through two nested levels
(30 of 34, then 17 of 64), and out of a search result back to the query
item (4 of 15, then 21 of 64). Back performs no network request.

## 2.11 Why KERNAL disk I/O cannot work from this program (2026-08-31)

Attempting "save this article to device 8" produced a definitive answer to
a question this project has failed at three times. The conclusion is not
"it is fiddly": it is that **KERNAL disk I/O and this program cannot
coexist**, for a measured reason.

### The measurements

A progress marker written after each stage, read back with
`m65 --memsave` after each hang:

| Configuration | Result |
|---|---|
| Full client (~41KB), interrupts **enabled** | hangs at `cli` itself (stage 2) |
| Full client, interrupts **masked** | `OPEN` never returns (stage 7) |
| 2.7KB build + virtual D81, interrupts masked | `OPEN` never returns (stage 7) |

### Why

This program loads at `$2001` and is ~41KB, so it occupies **`$2001-$c0f1`**,
and its stack grows down from `$d000`. That collides with everything ROM
banking touches:

- `$01 = $3f` maps **BASIC ROM over `$a000-$bfff`** — our *code*.
- `$d030 = $64` maps **C65 ROM over `$c000-$cfff`** — our *statics and our
  stack*.

Both were in the original `gopher_kernal.c`, and both are fatal: execution
in `$a000+` reads ROM instead of our instructions, and a string scan in
`$c000+` reads ROM bytes that never reach a NUL.

Removing both is not enough, because the KERNAL **IRQ handler** needs that
same ROM layout. Simply executing `cli` hangs instantly — servicing one
interrupt runs our program's bytes as if they were ROM. And with
interrupts masked, `OPEN` waits forever on a timeout only the jiffy clock
can expire.

So: KERNAL disk I/O requires interrupts; interrupts require ROM where our
program lives. There is no banking arrangement that satisfies both.

### This supersedes the earlier explanation

`gopher_config.c` recorded the cause as `$d030` "fighting the 80-column
screen the client sets up". That was wrong. It was never about the screen
— it was about ROM being mapped over the running program. The suspicion in
that same comment that a safe implementation "probably has to avoid the
KERNAL altogether" was right, and now has evidence behind it.

It also explains why a standalone probe once wrote `probe.txt`
successfully: a small probe's code and data sit below `$a000`, so nothing
is shadowed and interrupts are safe. Program size is the hidden variable.

### What is finished, and what is not

Finished and correct, sitting behind `#define SAVE_ENABLED 0`:

- `S` in the pager, prompting with an editable filename.
- `build_save_suggestion()` — derives a CBM DOS name from the selector
  (`Arnold_Mühren` -> `ARNOLD-M-HREN`), 16 characters, alphanumerics kept,
  everything else folded to `-`.
- `kernal_write_text_store()` — streams the attic-RAM text store to a file
  a line at a time, because an article can reach ~316KB and cannot be
  buffered.

Not working: the write itself. The route out is to bypass the KERNAL —
hypervisor calls, or driving the F011 controller directly — which is a
separate piece of work, not an adjustment to what is here.

### Useful for the eventual implementation

`$ba` (decimal 186) holds the device number of the last KERNAL I/O
operation, i.e. the drive the program was loaded from. Measured as `8` on
this machine. It is in zero page, so it is readable without any banking
games, and gives the destination chooser (2.3) a sensible default for
free.

## 2.12 KERNAL saving: the banking is solved, the screen editor is not (2026-08-31)

Continuing from 2.11. Two of that section's conclusions were wrong, and
the corrected picture gets much closer to a working save.

### What changed

**The IRQ vector is fine.** `$0314` was measured at `$f9ec` -- inside
KERNAL ROM, which `$01 = $3e` already maps. The theory that BASIC 65 left
a vector pointing into our program was wrong.

**`cli` is survivable after all.** The hang depends entirely on `$d030`:

| `$d030` during `cli` | Result |
|---|---|
| `$44` (our normal setting) | hangs instantly |
| `$64` (C65 ROM at `$c000-$cfff`) | **survives** -- verified on hardware |

So the KERNAL IRQ handler needs the C65 ROM mapped at `$c000`, and 2.11's
"interrupts are simply impossible here" was too strong.

**`$01` never needs changing.** `$3e` already maps the KERNAL at `$e000`
and I/O at `$d000`. Setting `$3f` only adds BASIC ROM over `$a000-$bfff`,
which is our own code -- pure downside.

### The design that follows

Each KERNAL call is wrapped in a "window": set `$d030 = $64`, `cli`, make
the call, `sei`, restore `$d030 = $44`. Inside a window, `$c000-$cfff` is
hidden -- which holds part of our `.bss` and **all of our stack** -- so the
window must be raw assembly touching no C variables, no C calls and no
soft stack. Only registers, the hardware stack at `$0100`, and a staging
area in low memory.

Memory layout, from the link map:

```
.text    $204f-$5f3a     .rodata  $5f3a-$bbbb
.bss     $bbbb-$c735     stack    $d000 downwards
```

`.bss` straddles `$c000`, so a `static` buffer cannot be relied on to land
below it -- one was tried and the linker placed it at `$ca6e`, inside the
hidden window. The staging area is therefore pinned at a fixed address,
**`$1400-$15ff`**, verified free on hardware: a pattern written there
survived a full DHCP bring-up, menu fetch and article load with zero bytes
changed. It sits above the 80x25 screen (`$0800-$0fcf`) and below the load
address (`$2001`).

`kernal_write_text_store()` implements this: `k_open()`, repeated
`k_flush()` of up to 255 bytes, then `k_close()`, with the buffer refilled
from attic RAM by ordinary C between windows.

### The remaining obstacle

Enabling interrupts brings the **KERNAL screen editor** back to life, and
it takes the display back. After a save attempt the screen and `$1400`
both contained the same repeating garbage -- the display had been moved
onto our staging area.

That is a different problem from the banking, and it has an obvious next
move: point `$0314` at a minimal handler that only advances the jiffy
clock (`$a0-$a2`) and acknowledges the CIA timer, then restores registers
and `RTI`. Disk timeouts need the clock; they do not need the editor,
the keyboard scan or the cursor. Restore the original vector afterwards.

That is the next thing to try, and it is small. Saving stays behind
`SAVE_ENABLED 0` until it works.

## 2.13 Minimal IRQ handler: two obstacles down, one open (2026-08-31)

Continuing 2.12. The screen-editor problem is solved and OPEN now
succeeds; the write itself still blocks.

### Fixed: the screen editor

Interrupts must be on inside a window, but the KERNAL's own handler brings
the screen editor with it -- which took the display back and relocated it
over the staging area, leaving the screen and `$1400` holding identical
garbage.

A minimal handler now replaces `$0314` for the duration of a save. It
advances the jiffy clock (`$a0-$a2`), acknowledges CIA1 (`$dc0d`) and the
VIC (`$d019`), restores registers and `RTI`s -- 24 bytes, living at
`$1560` inside the same verified-free page as the staging area. Disk
timeouts need the clock; they do not need the editor, the keyboard scan or
the cursor. The original vector is saved and restored around the save.

**Result: no screen corruption, and `OPEN` returns `ST = $00`.** The
filename staged correctly (`ARNOLD-M-HREN`), device 8, and the original
vector (`$f9ec`) was captured and restored.

### Open: CHROUT blocks

The write then hangs in the `CHROUT` loop, with `chunklen` stuck at 255
and `ST = $00`.

The obvious explanation is that there is no disk in the drive: CBM DOS
does not verify media at `OPEN`, so the first `CHROUT` that forces a
sector write waits forever, somewhere Run/Stop cannot reach.

A non-blocking guard was added -- read `$d083` DISKIN before touching the
KERNAL, and refuse with "No disk in drive" -- and **it did not prevent the
hang**, which is the genuinely confusing part. Reading the same registers
externally with `m65 --memsave` afterwards gives:

```
$d080 = $00   $d082 = $00   $d083 = $00   (DISKIN clear)
```

So the guard should have fired. Either the running program reads those
registers differently from the debug interface -- plausible, since the
F011 registers only appear at `$d080` in C65/VIC-III/IV I/O mode, and the
two paths may not agree on the mapping -- or DISKIN was set at the moment
the guard ran.

### Next steps

1. **Record what the program itself reads.** Store the DISKIN byte into
   the staging area at guard time and compare it with what `memsave`
   reports. If they disagree, the guard needs a different media test (or
   the drive needs selecting and the motor spinning first: `$d080 = $60`
   per the chipset reference, before status means anything).
2. **Test with a disk genuinely mounted**, via the machine's own disk
   menu rather than `m65 -d` -- the virtual-F011 route destabilised the
   machine repeatedly and left it needing a power cycle. If `OPEN` plus
   `CHROUT` then completes, the implementation is correct and only the
   no-media guard is outstanding.

Saving remains behind `SAVE_ENABLED 0`. Everything else -- the UI, the
filename derivation, the windowed writer, the IRQ handler, the staging
area -- is in the tree and working up to the point described.

## 2.14 Saving with a real disk: CHROUT blocks at 162 bytes (2026-08-31)

The machine auto-mounts `MEGA65.D81` on device 8, so the earlier
"no disk" theory in 2.13 was wrong. With that established, the picture is
much sharper.

### Corrected: the media guard was right, the debug reading was not

`$d083` read **from inside the running program** is `$08` -- DISKIN set,
media present. `m65 --memsave` on the same register reports `$00`.

**The two disagree.** The F011 registers only appear at `$d080` in
C65/VIC-III/IV I/O mode, and the debug interface evidently does not see
the same mapping as the program. So 2.13's confusion ("the guard should
have fired but didn't") was a measurement artefact: the guard behaved
correctly and correctly let the write proceed.

*Lesson: verify I/O register reads from inside the program. `--memsave` is
reliable for RAM and not for this.*

### What actually happens

With a real disk mounted:

| Stage | Result |
|---|---|
| media guard | passes, DISKIN set |
| `OPEN` | succeeds, `ST = $00` |
| `CHKOUT` | succeeds |
| `CHROUT` | writes **162 bytes**, then blocks |

Sampled four times over ~25 seconds: `progress` frozen at exactly 162,
`ST = $00`, still inside the flush window. Deterministic, not slow.

The natural next suspicion is the KERNAL's own DOS buffer. If it lives in
`$c000-$cfff`, then during a window -- where `$d030 = $64` maps C65 ROM
over exactly that range -- the KERNAL would be writing its buffer into
ROM. That would explain a hang once enough bytes accumulate to force a
real sector write, and it would mean the windowed-KERNAL approach cannot
work at all, pushing this back to F011-direct.

That is a hypothesis, not a finding. It is the first thing to test.

### Next steps

1. **Zero the instrumentation at the start of each save.** A follow-up run
   that capped the write at two lines returned `progress = 162` again --
   almost certainly stale, since RAM is not cleared by reset and the
   counter is only written inside the loop. That ambiguity wasted a cycle.
2. **Find where the KERNAL keeps its DOS buffer for device 8.** If it is
   in `$c000-$cfff`, the windowed approach is dead and F011-direct is the
   answer.
3. **Try a genuinely tiny file** (a dozen bytes) with the instrumentation
   zeroed. If that completes and appears in the directory, the write path
   is sound and the boundary is a buffer-flush problem.

Saving remains behind `SAVE_ENABLED 0`.

## 2.15 CHROUT needs the window; PROT is set; F011 reads are banking-dependent (2026-08-31)

Three more measurements, one of which may be the whole answer.

### CHROUT needs the window, so the CBDOS theory is dead

2.14 guessed that the `$d030 = $64` window was hiding CBDOS workspace and
causing the stall. Tested directly, with a disk mounted:

| flush environment | bytes written |
|---|---|
| inside the window (`$d030=$64` + `cli`) | 162, then blocks |
| outside it (normal banking, interrupts masked) | **0**, blocks immediately |

So `CHROUT` needs interrupts exactly as `OPEN` does. The window helps; it
is not the problem. That theory is wrong and should not be revisited.

### F011 registers read differently inside and outside the window

The IRQ handler now mirrors `$d082`/`$d083` into `$1418`/`$1419` on every
interrupt, since those registers cannot be read usefully from outside the
machine. During a stall, sampled from inside a window:

```
$d082 = $02   PROT set
$d083 = $00   DISKIN clear
```

But the guard, reading `$d083` **outside** the window, gets `$08` --
DISKIN set. Same register, same session, opposite answers.

So the F011 register view depends on the banking in force, presumably
because `$d080-$d08f` only appears there in C65/VIC-III/IV I/O mode and
`$d030` changes that. **Neither reading can be trusted without
establishing which mapping is in force.** This has now produced two
false conclusions (a "missing disk" that was present, and possibly this
PROT reading), and is the single most misleading thing encountered.

### Lead: PROT may be real

If `MEGA65.D81` is genuinely mounted write-protected, that explains
everything: CBM DOS `OPEN` for write succeeds regardless, and the write
then fails or stalls. It would make this a configuration issue rather than
a code defect.

Worth checking before any further debugging. If the disk is writable, the
`$02` is another artefact of the mapping problem.

### Also unexplained: the stall point is not stable

Two runs with nominally the same window configuration gave `progress =
162` and `progress = 0`. The only difference was a longer IRQ handler.
Either drive state carries across attempts (motor already spinning), or
there is a timing dependency. Instrumentation is now zeroed per save, so
these are not stale values.

### Where to resume

1. **Confirm whether the mounted disk is write-protected.** Cheapest
   possible test, and it may end the investigation.
2. If writable, establish which `$d030` setting gives a valid F011
   register view, and re-read PROT/DISKIN under that setting only.
3. Only then chase the stall point.

Saving stays behind `SAVE_ENABLED 0`. The client is unaffected and
verified working.

## 2.16 Six hypotheses eliminated; zero-page collision is the live one (2026-08-31)

The KERNAL save still stalls, but the search space is now much smaller.
Recorded mainly so none of this is re-tried.

### Eliminated, each by direct measurement

| Hypothesis | Verdict |
|---|---|
| No disk in the drive | **No.** Program reads `$d083 = $08`, DISKIN set |
| Disk is write-protected | **No.** User created and deleted a file on it |
| The window hides CBDOS workspace | **No.** Without the window, CHROUT moves *0* bytes instead of 162 -- the window helps |
| The window hides the F011 registers | **No.** `$d082`/`$d083` read identically under `$d030 = $44` and `$64` |
| CBDOS needs the real KERNAL IRQ | **No.** With the KERNAL's handler, OPEN itself never returns -- strictly worse than the minimal one |
| The JTAG link disturbs disk timing | **No.** Save triggered, then 75s with no memsave and no screenshot: identical stall |

The JTAG question was a good one -- `m65` halts the CPU to read memory,
and every earlier observation was taken *during* the write. It is now
ruled out, and the earlier `PROT` reading is explained as a genuine
transient sampled mid-operation rather than an artefact.

### The live hypothesis: zero page

From the link map:

```
llvm-mos zero-page usage spans $22-$90
```

`$90` is the KERNAL's **ST**, the I/O status byte that every KERNAL I/O
routine reads and writes. Nearby lie `$9a` (current output device) and
`$b7-$bf` (filename length, device, secondary address, name pointer) --
all of which OPEN, CHKOUT and CHROUT depend on.

If the compiler has allocated variables over the KERNAL's zero page, then
ordinary C between windows corrupts the KERNAL's I/O state, and the KERNAL
corrupts ours. That fits the symptom exactly: OPEN succeeds, CHROUT works
while it is only buffering, and the whole thing wedges once real I/O state
matters.

It also explains the instability -- 162 bytes one run, 0 the next -- since
what gets clobbered depends on which variables were live.

### Next step

Constrain llvm-mos's zero page to stay clear of the KERNAL's. If the
toolchain exposes the ZP range (a linker symbol or a codegen flag), cap it
below `$90` -- ideally below `$8f` -- rebuild, and retry the save
unchanged. That is a build-configuration change, not a code change, and it
is the cheapest remaining test by a wide margin.

If that fixes it, the whole windowed-KERNAL design is vindicated. If not,
switch to driving F011 directly: it needs no KERNAL, no interrupts and no
banking games, so it sidesteps every problem in 2.11-2.16, and the chipset
reference documents the registers fully.

Saving stays behind `SAVE_ENABLED 0`.

## 2.17 KERNAL route: recommend abandoning it (2026-08-31)

### The ethernet interrupt lead, and why it did not resolve things

`trampoline.asm` already recorded that `cli` hangs once `ETH_INIT` has
run, blaming "an interrupt nothing is set up to service". That is the
45E100: `$d6e1` bit 7 (RXQEN) and bit 6 (TXQEN) enable its RX/TX
interrupts, and the minimal IRQ handler acknowledges CIA1 and the VIC but
not the ethernet controller. With those enabled the controller re-asserts
immediately and the CPU never leaves the handler -- so the save was not
deadlocked but *starved*, which fits 162 bytes in one run and 0 in the
next.

That explanation is almost certainly correct as far as it goes. Disabling
RXQEN/TXQEN across the save (read-modify-write, since the low bits of
`$d6e1` are the RX queue advance controls) changed the failure mode --
the display corrupts differently -- but `CHROUT` still moves zero bytes.

So the interrupt storm was real and is not the whole story.

### Recommendation: stop here and drive F011 directly

Seven hypotheses have now been tested and eliminated (see 2.16 plus the
above). Each fix has produced a different failure rather than progress,
and the remaining unknowns are all inside a C65 KERNAL whose disk layer is
not documented at the level this needs.

Driving F011 directly avoids **every** problem encountered in 2.11-2.17,
by construction:

| Problem | F011-direct |
|---|---|
| `$01`/`$d030` banking hides our code, data or stack | no banking change needed |
| KERNAL I/O requires interrupts | none required |
| KERNAL IRQ needs C65 ROM at `$c000` | no IRQ needed |
| KERNAL screen editor steals the display | never runs |
| 45E100 interrupt storm under `cli` | interrupts stay masked throughout |
| CBDOS internals undocumented | F011 registers fully documented |

The cost is implementing CBM DOS: read the BAM on track 40, allocate
blocks, write the file as a linked chain (2 link bytes + 254 data bytes
per block), add a directory entry, write the BAM back. That is a known,
bounded, testable job against a documented register interface -- unlike
the current situation, which is guesswork against a black box.

The chipset reference documents everything needed: `$d080` motor and drive
select (`$60` to enable), `$d081` commands, `$d082` BUSY/DRQ/RNF/PROT,
`$d083` DISKIN, `$d084-86` track/sector/side, `$d087` data. There is also a
section on how the hypervisor virtualises F011 for mounted `.d81` images,
which is what device 8 is here.

### What is worth keeping

Everything above the disk layer is done and correct, and would be reused
unchanged:

- `S` in the pager, with an editable pre-filled filename.
- `build_save_suggestion()` -- selector to a legal 16-character CBM DOS name.
- The chunked staging design and the verified-free buffer at `$1400-$15ff`.
- `gopher_screen_init()` teardown/rebuild around the operation.

Only `k_open`/`k_flush`/`k_close` and the IRQ handler would be replaced.

Saving stays behind `SAVE_ENABLED 0` until then.

## 2.18 F011 direct access works (2026-08-31)

### The KERNAL route is definitively dead

Final elimination, and the one that settles it: the user loaded the client
**from disk** (`LOAD"GOPHER",8` off a mounted `.d81`) with the **JTAG cable
unplugged**, and the save stalled identically with nothing written.

That rules out the last two doubts -- that the debug link interfered, and
that `m65 -r` injection left CBDOS uninitialised because the KERNAL had
never performed a real disk operation. Neither. The defect is intrinsic.

### F011 direct access: working, verified

`src/gopher_f011.c` reads a physical sector with **no KERNAL, no
interrupts and no banking changes**. Reading the D81 header -- CBM track
40 is physical track 39, side 0, sector 1 -- returns:

```
[00-01] first dir t/s : 40,3            correct for a 1581
[02]    DOS version   : $44 'D'
[04-13] disk name     : 'M65 MENU SYSTEM '
[16-17] disk ID       : '20'
```

That is the real header of the auto-mounted `MEGA65.D81`, so the whole
path -- register protocol, hypervisor virtualisation of a mounted image,
and the 512-byte transfer -- works.

### One trap worth knowing

**SPINUP never completes on a virtualised drive.** The chipset reference
says to write `$60` to `$d080`, then `$20` (SPINUP) to `$d081`, and wait
for BUSY to clear. Against a mounted `.d81` there is no physical motor:
BUSY stays set and `$d082` reads `$b0` (BUSY|EQ|RNF), which on a real
drive would mean failure. **Treating that as an error rejects every
read.** `f011_start()` reports it but does not fail on it, and RNF is
checked only *after* the transfer, where it reflects the read rather than
the unserviced spin-up.

### What remains for saving

The read primitive is the foundation; writing a file means implementing
CBM DOS on top of it:

1. **Write primitive** -- same protocol with the WRCMD bit (`$d081` bit 7)
   instead of RDCMD, filling the buffer through `$d087` first.
2. **Sector mapping** -- CBM track 1-80 / sector 0-39 to physical
   track-1 / side = sector/20 / sector = (sector%20)/2+1, plus which
   256-byte half of the 512-byte physical sector.
3. **BAM** -- read track 40, find and allocate free blocks, write it back.
4. **File chain** -- 2 link bytes + 254 data bytes per block.
5. **Directory entry** -- on track 40: name, type, start track/sector,
   block count.

Steps 1 and 2 are mechanical and testable in isolation (write a sector,
read it back, compare). Steps 3-5 are the real work, and the part where a
bug corrupts the user's disk -- so they should be developed against a
scratch `.d81`, never the auto-mounted one.

## 2.19 F011 write primitive and CBM block mapping (2026-08-31)

### Mapping validated on hardware

`f011_read_block()` / `f011_write_block()` translate CBM logical blocks to
the physical geometry:

```
physical track  = cbm_track - 1
side            = cbm_sector / 20
physical sector = (cbm_sector % 20) / 2 + 1
half            = cbm_sector % 2          (which 256 bytes of 512)
```

Verified by reading CBM (40,3) -- the first directory block of a 1581 --
which maps to physical track 39, side 0, sector 2, second half. The result
was a real directory:

```
next dir block link: t0, s255        end of chain, correct convention
entry 1: type=$82 (PRG) start=t39,s0 name='MENU'
```

`MENU` is an actual file on the mounted `MEGA65.D81`, so the track offset
and the half-sector selection are both right.

### Write primitive: implemented, NOT yet tested

`f011_write_sector()` follows the documented procedure:

- Pre-fill the controller's 512-byte buffer through `$d087`. The
  byte-at-a-time variant (`$85`) is explicitly discouraged for SD-backed
  and virtualised images, where the transfer completes instantly and bytes
  cannot be supplied in time.
- Open the SD **write gate**: `$57` to `$d680` opens it for all sectors
  above 0 for roughly a millisecond (`$4d` is the separate gate for the
  master boot record and must never be used here). It closes on its own,
  so it is opened immediately before the command.
- Command `$84` -- `$80` write plus `$04` write-precompensation.

`f011_write_block()` is read-modify-write, since a CBM block is half a
physical sector and the other half must be preserved.

**None of this has been executed.** The only disk mounted is the user's
auto-mounting `MEGA65.D81` menu disk, and a bug in an untested write path
would corrupt it. Write testing needs a scratch image mounted --
`SAVETEST.D81` is already on the SD card for this purpose.

First write test should be: write a known pattern to a block on an unused
track, read it back, compare, and confirm the *other* half of the physical
sector is unchanged.

### A process note

Three insertion scripts reported success without asserting the
replacement had matched, so a probe that was never inserted appeared to
run and returned stale RAM as if it were data. Two debugging cycles were
spent on those readings. Every source edit here should assert its pattern
matched before reporting success.

## 2.22 CBM DOS writer complete; blocked on RAM (2026-08-31)

`src/gopher_cbmdos.c` implements the filesystem layer on the working F011
primitives. It is written and reviewed but **has never been executed**,
because wiring it into `save_article()` overflows RAM by 655 bytes.

### What it does

A streaming API, because an article can reach ~316KB and cannot be
buffered:

```c
cbmdos_create(name, drive);   cbmdos_put(b);  ...   cbmdos_close();
```

- Loads the BAM from (40,1) and allocates nearest the directory track
  first, as CBM DOS does, so files do not scatter.
- Allocates only on tracks 1-39, whose BAM lives entirely in that one
  sector -- ~396KB, far more than any article, and it never touches the
  second BAM sector or the directory track's own allocation.
- Chains data blocks: 2 link bytes + 254 data; the final block's link is
  track 0 with the index of the last byte used.
- Finds a free slot in the existing directory chain and writes a closed
  SEQ entry ($81) with start block, `$a0`-padded name and block count.
- Writes the BAM back once, at close.

Working buffers are at `$1800-$19ff`, verified free on hardware (1024
bytes written there survived a full DHCP bring-up, menu fetch and article
load with zero changes). An earlier note calling that region unsafe was
wrong -- it came from a probe that was never actually inserted.

### The blocker, measured

Baseline with the module present but unreferenced:

```
.text    $204f-$5f10   16065 bytes
.rodata  $5f10-$bb91   23681 bytes
.bss     $bb91-$c70a    2937 bytes
free to stack:          2294 bytes
```

Wiring the save path costs about 2.9KB of code, which overflows by 655.

### The biggest lever is not ours

The largest single `.bss` item is **`escapeCode`, 765 bytes** --
`static ESCAPE_CODE escapeCode[255]` in mega65-libc's `conio.c`. It is a
PETSCII control-code dispatch table, initialised by `conioinit()`, which
this client calls, so LTO cannot drop it. Only a handful of entries are
ever populated.

Shrinking it would very nearly close the gap on its own, but `conio.c`
lives in the shared `mega65-libc` checkout, so the change
would affect anything else built against that tree. **That is a decision
for the user, not a unilateral edit.**

Other candidates, all ours and all safe to move to the verified-free low
RAM at `$1a00-$1bff` (512 bytes) or further into `$1000-$1fff` (untested
beyond what is listed):

```
 160  rec                    160  fetch_text.linebuf
 160  fetch_menu.linebuf     148  dns_cache
 127  main.urlbuf            127  choose_start_site.urlbuf
 115  home_loc               115  current_loc
 100  uiline                  81  xlate_buf
```

Relocating four or five of those would also close the gap, at the cost of
more fixed-address buffers to keep track of.

### The real shape of the problem

`.rodata` is 23,681 bytes, nearly all of it the embedded `eth_payload`
copied into bank 4 once at boot and never read again. It occupies the
`$5f10-$bb91` window for the entire run. Moving it out -- loading it from
disk, or staging it through attic RAM -- would free ~22KB and end this
class of problem permanently, rather than reclaiming a few hundred bytes
at a time. That is a larger change and should be weighed on its own.

```

chaining and directory writing are all correct. Three consecutive saves
in one session all succeeded.

### The stack that made it work

| layer | role |
|---|---|
| `gopher_f011.c` | sector read/write, CBM<->physical mapping, drive select |
| `gopher_cbmdos.c` | BAM allocation, block chaining, directory entry |
| `gopher_scratch.h` | fixed-address buffers in verified-free low RAM |

No KERNAL, no interrupts, no banking changes anywhere in it.

### How the memory was found

Wiring the disk layer in overflowed RAM by 655 bytes. The fix was to move
buffers out of `.bss` into low RAM below the load address, in three
regions each verified by writing a pattern and confirming it survived a
full DHCP bring-up, menu fetch and article load untouched:

```
$1400-$15ff   $1a00-$1bff   $1c00-$1fff
```

Thirteen buffers moved. Two things made this pay off far beyond the bytes
reclaimed: constant addresses generate much better code than `.bss` arrays
on this target (`.text` fell by over 5KB), and the freed `.bss` compounded
with it. Final state: **486 bytes free** against a measured 133-byte peak
stack, with the whole save feature enabled.

### Two mistakes worth recording

**Aliasing the buffers onto `eth_payload` was wrong twice over.** The
payload is dead after `gopher_boot_load()` copies it to bank 4, so reusing
its 22KB looked free. But writing through a `const` object is undefined,
and LTO duly folded the reads back to the original payload bytes and
painted them on the screen. Making the payload non-const then cost so much
optimisation that only 123 bytes of stack remained -- below the measured
peak. Fixed low RAM was the right answer.

**Converting arrays to pointers silently broke every `sizeof()` on them.**
`sizeof(ptr)` is 2, so bounded copies truncated to nothing and the screen
went nearly blank. Explicit length constants now live beside the addresses
in `gopher_scratch.h`.

### Remaining

- The filename prompt pre-fills with the derived name and typing *appends*
  to it, so `TEST1` became `ARNOLD-M-HREN1`. Correct per the pre-fill
  design, but a first keystroke that replaces the suggestion would be
  friendlier.
- No duplicate-name check: saving twice with the same name will create a
  second entry. `CBMDOS_ERR_EXISTS` is defined but never returned.
- Only device 8 is offered. `f011_start()` takes a drive number and the
  mapping is drive-agnostic, so the 8/9 chooser from 2.3 is now a UI job
  rather than a disk one.
- Type is SEQ (`$81`). Fine for text; binary downloads would want PRG.

slot 6: type=$81 start=t39,s0  blk=20   'ARNOLD-M-HREN'   <-- GOPHER's first block
```

`GOPHER` is 165 blocks from t39,s0, so it occupies tracks 39-36 entirely
and t35 sectors 0-4. Slots 5 and 6 were therefore allocated blocks already
in use, and writing them **overwrote part of another file**.

### Why the earlier result was misleading

The first four saves (slots 1-4) allocated correctly: t35s5, t34, t33,
t32, walking downward exactly as intended. That looked like proof the BAM
logic worked. It was not -- it only showed that it worked four times in a
row within a short window.

The lesson: "three consecutive saves succeeded" is evidence about the
*write path*, not about *allocation correctness*. Allocation can only be
judged by checking the results against what is already on the disk, which
is what eventually exposed this.

### Where to look

`bam_find()` returned blocks whose bits it should have seen as allocated,
so either the BAM read back from disk does not reflect earlier
allocations, or the bit arithmetic is wrong. Candidates:

1. **`bam_save()` may not be persisting.** It writes CBM (40,1), which
   shares a physical sector with the header at CBM (40,0), so
   `f011_write_block()` does read-modify-write across the disk header. A
   fault there could leave the BAM stale or corrupt.
2. **Free-count versus bitmap disagreement.** `bam_find()` skips a track
   whose count byte is zero. If count and bitmap disagree, allocation
   walks into blocks the bitmap says are free.
3. **The 1581 BAM may not be laid out as assumed** -- entry stride,
   base offset, or which BAM sector covers which tracks.

The first check should be non-destructive: read CBM (40,1) and decode the
per-track free counts and bitmaps, then compare them against the file
chains actually present in the directory. If the BAM on disk disagrees
with reality before any save, the fault is in the layout assumptions
rather than in `bam_save()`.

### What still stands

The layers below are unaffected and remain verified:

- `f011_read_sector` / `f011_write_sector` -- pattern written, read back,
  neighbouring half preserved.
- CBM <-> physical mapping -- validated against a real directory.
- Block chaining and directory-entry writing -- the files that *were*
  allocated correctly are well-formed and readable.

Only block *allocation* is wrong, and it is the one part that can damage a
disk.

### Also outstanding

- ASCII to PETSCII translation was added to the save path but never
  verified on disk, because the test keyboard stopped delivering typed
  characters to `read_line` and every attempt saved under the pre-filled
  name, colliding with earlier files.

## 2.26 Root cause found: the sector buffer pointer (2026-08-31)

Following 2.25, which had narrowed the fault to the write path.

### The bug

`f011_read_sector()` and `f011_write_sector()` moved data through the
DATA register at `$d087`, one byte at a time. That register walks an
internal pointer into the controller's 512-byte sector buffer, and
**nothing in the documented sequence resets that pointer before a write**.
A read leaves it at the end of the buffer, so the next write began
part-way through and stored the data displaced -- exactly the symptom in
2.25, where valid BAM entries appeared about seven bytes off.

### The fix

The chipset reference documents a second, better method: the sector
buffer is **memory-mapped at `$ffd6c00-$ffd6dff`**, with BUFSEL (bit 7 of
`$d689`) cleared so the floppy buffer is visible rather than the SD
card's. Both transfers now use it, via `lcopy`:

```c
F011_BUFSEL = F011_BUFSEL & 0x7f;
lcopy(F011_SECBUF, (unsigned long)out, 512);          /* read  */
lcopy((unsigned long)src, F011_SECBUF, 512);          /* write */
```

No pointer, no ordering dependency, and a DMA copy rather than a
512-iteration byte loop -- the binary shrank by about 3KB as well.

### Verified

Reading the BAM through the new path returns a valid structure where the
old path returned zeros:

```
link=40,2  DOS=$44  ~DOS=$bb
track 34: count=40  bitmap=ffffffffff
track 35: count=40  bitmap=ffffffffff
track 40: count=36  bitmap=f0ffffffff
```

That is a correctly-formed, internally consistent 1581 BAM.

### NOT yet verified

**Whether saving now allocates correctly.** The network went down before
that could be tested: DHCP began failing consistently, and it is not
this project's doing -- the same failure occurs with `SAVE_ENABLED 0`,
where LTO drops every line of the disk code. Environmental, and it blocks
the test because an article has to be fetched before it can be saved.

Saving therefore stays behind `SAVE_ENABLED 0` until a save has been run
and the resulting BAM and directory checked against what was already on
the disk -- the check that was skipped in 2.23 and led to the incorrect
"it works" claim.

### To resume

1. Get networking back (see below), then fetch any article.
2. Save twice, with distinct names.
3. Read back the BAM and directory and confirm: two entries, distinct
   start blocks, and BAM counts decremented consistently with the bitmaps.

The disk on the card is currently an empty `SAVETEST.D81` -- tracks 34

## 2.28 Out of address space; what unblocks it (2026-09-01)

Saving works and is verified (2.27). Everything queued behind it is now
blocked by memory, not by difficulty.

### Measured

```
shipped build (save, no extras)   273 bytes free   margin 140 over the
                                                   133-byte stack peak
+ duplicate-name check              7 bytes free   not shippable
+ drive 8/9 chooser (minimal)      48 bytes free   not shippable
```

Both features are written and correct; neither fits. The chooser is a
dozen lines, since `f011_start()` already takes a drive number.

Priority noted: **drive selection matters more than duplicate checking.**
Neither is in the shipped build.

### Levers already spent

Nineteen buffers now live at fixed addresses in low RAM below the `$2001`
load address, across four regions each verified free on hardware by
pattern test:

```
$1000-$13ff   $1400-$15ff   $1a00-$1bff   $1c00-$1fff
```

Two lessons from doing it. Use `#define NAME ((char *)0xADDR)` so accesses
are constant addresses -- assigning to a local `char *` instead costs a
pointer set-up per call and made the binary *larger* than the `.bss`
arrays it replaced. And converting an array to a pointer silently changes
`sizeof()` to 2, which truncated several bounded copies before it was
caught.

### The lever that looked promising and is not

`escapeCode` in mega65-libc's `conio.c` is 765 bytes -- by far the largest
single `.bss` item, and it is not ours. But it is indexed up to 255
through a computed hash (`escapeCode[escHash]`), so it cannot be shrunk
without reworking third-party dispatch logic. Not worth it.

### What actually unblocks everything

`.rodata` is ~23.5KB, nearly all of it `eth_payload` -- the second stack's binary,
embedded in the program, copied to bank 4 once by `gopher_boot_load()` and
never read again. It occupies the address space for the entire run.

**Load it from disk at boot instead.** That was impossible earlier because
there was no way to read a file; there is now. `gopher_f011.c` and
`gopher_cbmdos.c` already read sectors, map CBM blocks, and walk the
directory -- reading a file is following a block chain, which is simpler
than the writing already implemented.

- Ship `ETH.BIN` as a second file on the `.d81`, which FR-0b allows.
- At boot, find it in the directory and stream its blocks into bank 4.
- Delete the embedded array.

That frees roughly **22KB** -- not the few hundred bytes this section has
been fighting over -- and ends this class of problem rather than deferring
it. It also makes updating the second stack a matter of replacing a file on the
disk instead of regenerating a C array.

Risk is low: it runs before the network, needs no interrupts or banking,
and if the file is missing the client can say so plainly instead of
failing obscurely.

## 2.30 Drive chooser; two bugs it exposed (2026-09-01)

The 8/9 save-destination chooser, which §2.28 could not fit and §2.29
unblocked. 494 bytes; 20,966 still free below the stack.

**Behaviour.** After the filename prompt: `Save to drive 8 or 9?
(Return = 8, Stop cancels)`. `8`/`9` choose, Return keeps the previous
choice, Stop cancels. The choice is remembered between saves, so filing
several articles onto one disk is a single keypress. Device 8 is F011
drive 0 and device 9 is drive 1; the result line names the drive used.

**No disk-presence pre-check.** The obvious test, DISKIN in `$d083`, is
unreliable against a mounted `.d81` for the same reason SPINUP is: the
drive is virtualised and the status bits do not mean what they would on
real hardware (see `f011_start`). A wrong pre-check would refuse a save
that would have worked, so the write is attempted and any failure
reported. All F011 waits are bounded at 60,000 iterations, so a missing
disk returns an error rather than hanging — verified by saving to drive 9
with nothing mounted there.

**Verified on hardware:** saved to drive 8, pulled the image back over
serial, confirmed a SEQ entry of 5 blocks / 1,080 bytes / 27 lines whose
decoded text matches the pager. Drive 9 with no disk reports
`SAVE FAILED - PROXY` and returns cleanly. The remembered-choice path was
checked too: after the drive 9 failure the prompt correctly offered
`Return = 9`.

### Two pre-existing bugs this surfaced

**1. Filename padding — saved files could not be LOADed by name.**
`cbmdos_close()` wrote the 16-byte name as `fname[i] ? fname[i] : 0xa0`,
testing each byte independently. Past the terminating NUL that reads the
reusable scratch buffer's leftovers from the previous save, so `PROXY`
landed on disk as `50 52 4f 58 59 a0 4a a2 25 20 c1 ...`. CBM DOS matches
names exactly, so `LOAD"PROXY"` could never have worked — which bears
directly on the earlier question about reading a saved file back from
BASIC. Now pads with `$a0` from the terminator onward. Same class of bug
as the `dir_find_name` one in §2.29: walking a C string past its NUL to
synthesise CBM padding. Both sites are now explicit about where the name
ends.

**2. Four scratch buffers were on occupied memory.**
`SCR_SAVE_RESULT` (`$1000`), `SCR_SAVE_SUGGEST` (`$1040`),
`SCR_DOS_NAME` (`$1060`) and `SCR_DOS_LINE` (`$1080`) were documented as
"verified free". They are not. Dumped from hardware, `$1000` holds BASIC
65's function-key definition table — `DIR`, `DIR "*=PRG"`, `KEY6`,
`MONITOR`, `HELP`, `RUN "*"` — and `$1060-$10ff` holds live 6502 code.

The collision was invisible while nothing re-initialised that area, which
is why saving to drive 8 worked throughout §2.27. It surfaced on the
failing drive 9 save: the ROM rewrote the fkey table between the `strcpy`
of the error prefix and the `strcat` of the filename, and the status line
read `.....DIR."*=PRG"..KEY6..MONITOR..PROXY`.

Moved into `.bss`. The fixed-address scheme existed only because `.bss`
had no room; §2.29 removed that constraint, so 178 bytes of buffer now sit
where the linker guarantees they are nobody else's. The regions from
`$1400` up were verified differently — a pattern written and re-read after
a full DHCP bring-up, menu fetch and article load — and stay put.

**Lesson worth keeping:** "verified free" meant two different things in the
same header. The `$1800` regions had an actual experiment behind them; the
`$1000` ones inherited the phrase without one. A claim of verification
should say what was done, or it is not a claim.

**Also fixed:** every error exit in `cbmdos_create`, `cbmdos_put` and
`cbmdos_close` returned without calling `f011_stop()`, leaving the drive
motor and LED running after a failed save. All error paths now stop the
drive.

## 2.32 Version/contact line; screen-code table corrected (2026-09-01)

The startup screen now reads:

    MEGA65 Gopher Client - version 0.1

`GOPHER_VERSION` is defined once at the top of `gopher.c`. Only the startup
screen carries it; the chooser, URL-entry and "Connecting to ..." screens
keep the plain title, since they are transient in-flow screens rather than
a splash.

(A byline naming the author and a contact address were shown here for a
time, and were removed before the repository was made public.)

### The screen-code table was wrong above 'Z'

Printing an email address exposed a long-standing bug.
`gopher_ascii_to_screencode()` passed `$40-$5f` straight through as if
screen code equalled ASCII. It does not. In this charset those codes are
graphics glyphs:

| char | was | rendered as | correct |
|---|---|---|---|
| `@` | `$40` | horizontal line | `$00` |
| `[` | `$5b` | `+` | `$1b` |
| `]` | `$5d` | `|` | `$1d` |
| `_` | `$5f` | corner block | `$64` (low bar) |
| `^` | `$5e` | graphic | `$1e` (up arrow) |
| `\|` | (fallback) | `.` | `$5d` (vertical bar) |

So `[DIR]` had been rendering as `+DIR|` on **every menu line**, and
underscores as a block -- which is why gopher ASCII-art banners looked
like noise. All fixed and legible now.

`|` was not in the passthrough range at all: ASCII `$7c` fell to the `.`
fallback. The vertical-bar glyph is at screen code `$5d` -- exactly the
glyph `]` was wrongly rendering as. Since gopher ASCII art is built largely
from `|` and `_`, mapping it turned the gopherpedia banner from noise into
clean lettering.

**Still lossy, by charset limit rather than bug:** `\\`, `{`, `}`, `~` and
`` ` `` have no glyph here. Backslash is the one that shows, since art uses
it for right-leaning diagonals; the diagonal graphics live at `$4d`/`$4e`,
which in the lower/mixed charset are `M` and `N`, so they are unreachable.
Those characters render as `.`.

**`@` needed more than a table entry.** Its screen code is `$00`, which
`xlate()` used as its terminator, so `cputs()` would have stopped at the
`@` and printed `mega65`. `xlate()` now returns a length and `put_xlated()`
prints the runs between embedded `$00` bytes, emitting each `@` with
`cputc(0)`. Runs still go through `cputs()`, which is DMA-backed, so
ordinary text costs nothing extra; only the rare `@` adds a call.

**Method note worth keeping.** The ASCII screenshot (`m65 -S`) is *not*
evidence for glyph questions: it maps screen codes back to ASCII, so it
reported a correct `@` and correct `[DIR]` while the screen showed neither.
Every claim above was checked against a **PNG capture** instead. For
anything about what the display actually shows, capture the PNG.

## 2.33 Duplicate-name check on save (2026-09-01)

`cbmdos_create()` now refuses a name already present in the directory,
returning `CBMDOS_ERR_EXISTS`, which the pager reports as
`Already on disk - NAME`. 20,233 bytes still free below the stack.

CBM DOS itself does not prevent this: a duplicate entry is accepted, the
older file becomes unreachable by name, and its blocks stay allocated. The
check matters more here than in a general-purpose DOS because the suggested
filename is derived from the selector, so two articles from one site
collide easily.

Implemented with the existing `dir_find_name()` -- written for the `ETHBIN`
loader in 2.29 and reused here. Compared against the case-folded name,
which is what would be written; a pre-existing lower-case entry would not
match, which is acceptable since every entry this program creates is folded
the same way.

**Verified on hardware, in sequence:**

1. Save as `PROXY` -> `Saved to drive 8: PROXY (27 lines)`
2. Save again as `PROXY` -> `Already on disk - PROXY`
3. Edit to `PROXY2` -> `Saved to drive 8: PROXY2 (27 lines)`

so a rejection does not leave the writer in a broken state.

**No block leak**, verified by comparing BAM free counts between the
pristine image and one read back after the three operations above: 3014 ->
3004, exactly the 10 blocks the two 5-block files occupy. The check returns
before `bam_load`/`bam_find`/`bam_alloc` and before any directory slot is
claimed, so nothing can be allocated on the rejected path -- and the
measurement confirms it rather than assuming it.

## 2.34 RESOLVED: every network failure hung the client (2026-09-01)

Root-caused and fixed. This was not a timeout problem and not a second-stack
problem: **the connect timeout fired correctly every time, and the code
that reports the error is what never returned.** Any DNS or connection
failure froze the machine on the "Connecting to ..." screen.

That makes it the explanation for the intermittent freezes seen earlier,
and it is worth noting how badly it was disguised: the last thing on screen
was "Connecting to ...", so it looked like a connect that never timed out.

### How it was found

Deterministic reproduction first: point the client at an unused LAN address
(`192.168.1.9`) so the connection can never succeed. That turned an
intermittent fault into a reliable one, which made everything after it
cheap.

Then instrumentation, because `--memsave` cannot see I/O registers -- the
frame counter at `$d7fa` reads back as 0 from the host even while the
client is plainly ticking, so state has to be copied into ordinary RAM to
be observable. Three volatiles in `.bss`: a phase byte set immediately
before and after **every** the far call, a spin counter incremented in
every wait loop, and the last `$d7fa` seen. A frozen "before" value would
have proved a call never returned.

The result was `phase = 26` (immediately *after* `CONNECT_POLL` returned)
with the spin counter frozen: no instrumented loop was running and no
the far call was blocked. Every candidate was eliminated and the answer
was still not in view.

What settled it was reading the CPU program counter directly from the
serial monitor. `m65` has no register dump, but the monitor protocol does;
macOS needs the `IOSSIOSPEED` ioctl to open the port at 2000000 baud, since
both `termios` and `stty` reject that rate. `r` returned
`PC = 4996  LDA ($08),Z`, and repeated sampling showed the PC cycling in
`$4986-$4998` -- inside `say_net_error`.

### The defect

`strcat(uiline, gopher_net_strerror())` compiled to a scan loop at `$497f`
whose pointer bytes (`$74`/`$75`) are loaded fresh each iteration and
**never updated inside the loop**, with the `Z` index also unchanged. The
pointer is invariant, so it re-reads one byte forever and exits only if
that byte happens to be zero. Equivalent `strcat` chains elsewhere (the
"Connecting to " line, a few lines earlier) compile correctly, so it is
specific to appending the pointer returned from `gopher_net_strerror()`.

No attempt was made to chase this into llvm-mos. `say_net_error` now builds
its lines with explicit bounded helpers (`ui_set`/`ui_add`/`ui_add_uint`)
that keep a running length instead of re-scanning.

**A second, plainer bug fixed at the same time:** the old code was
unbounded. `strcat(uiline, host)` could append up to 127 bytes of hostname
into the 100-byte `uiline`. The new helpers clamp at `SCR_UILINE_LEN - 1`.

### Verified on hardware

- Unreachable address now reports and returns to a usable state:
  `ERROR: Refused by host (nothing listening?)` / `Host:` / `Addr:` /
  `Tried 1 time` / `{press any key}`.
- Normal browsing unaffected; gopherpedia fetches and renders.
- Instrumentation removed afterwards. 20,431 bytes free below the stack.

**Note on the reported error text:** an address that nothing answers is
described as "Refused by host (nothing listening?)", which is the second stack
reporting `CONN_FAILED` where the truth is closer to "no route / no ARP
reply". Cosmetic, not chased.

### Method notes worth keeping

- Turn an intermittent fault into a deterministic one *before* doing
  anything else. Everything afterwards was cheap because of it.
- `--memsave` is unreliable on I/O registers; copy to RAM to observe.
- When instrumentation eliminates every candidate, stop inferring and read
  the PC. `mon.py` in the scratchpad does this; the only obstacle was the
  baud rate, and `IOSSIOSPEED` solves it.

## 2.35 The second stack's 100ms wait is now bounded (2026-09-01)

`ETH_WAIT_100MS` ended in a bare `beq -` waiting for `$D7FA` to change.
That is an unbounded spin: if the frame counter ever stalls the routine
never returns, and `ETH_INIT` calls it three times, so the client would
freeze permanently at "Bringing up network...". Our own earlier patch
introduced this shape while fixing the original raster bug -- it replaced a
dead clock with a live one but kept the unbounded wait.

Now bounded: 8 x 65536 polls, about 6.8M cycles or ~170ms at 40MHz,
comfortably longer than the 20ms a real frame takes, so a healthy machine
never trips it. On timeout the routine simply returns. A stack should
degrade, not hang.

### The layout trap this ran into

The obvious implementation -- three `.byte` scratch variables next to
`tmp_raster` -- silently breaks the client. the second stack's data block is
contiguous, so adding three bytes at that point pushes **every later label
up by three**, including:

    TCP_DATA_PAYLOAD       $311b -> $311e
    TCP_DATA_PAYLOAD_SIZE  $30f7 -> $30fa

and `gopher_net.c` addresses both by absolute value (`0x4311b`, `0x430f7`)
when it stages a request. The client would have written every gopher
request three bytes before the payload buffer, corrupting stack state on
each fetch. Nothing warns about this: the assembler is happy and the
binary is the same size.

The fix is to allocate no storage at all -- the three scratch bytes are
**symbol definitions** at `$75fd-$75ff`, inside the 385-byte padding gap
between the main data block (ending `$747e`) and `ML_EXTENSION_TABLE_BASE`
(`$7600`), placed at the far end so upstream has ~380 bytes of growth room
before it could reach them.

**Verified unchanged after the rebuild:** the jump table (`$2000-$2068`),
the ML extension table (`$7600-$773b`), `TCP_DATA_PAYLOAD` (`$311b`) and
`TCP_DATA_PAYLOAD_SIZE` (`$30f7`). On hardware: DHCP completes and
gopherpedia fetches and renders.

**A second trap worth recording:** `64tass -L` writes a *listing*; the
label file needs lowercase `-l`. `target/eth.labels` in the second stack
checkout is stale output from some earlier build, and reading it produced a
confident but wrong "nothing moved" conclusion. Generate labels fresh
before trusting them.

### What this says about the coupling

The client hardcoding addresses inside the second stack's data segment is fragile by
construction: any upstream edit before `TCP_DATA_PAYLOAD` silently breaks
request staging, with no build error and no obvious symptom beyond
corrupted transfers. Exporting those two addresses through the jump table,
or through the ML extension table, would remove the coupling. It is also a
concrete argument for the separate-stack discussion: a stack we own would
expose a stable ABI rather than raw offsets.

## 2.36 URL type characters; G:URL reaches text items (2026-09-01)

Found during the 2.33 regression pass: G:URL could not open a text file.
`parse_url()` stripped one `/` and treated the whole remainder as the
selector, so a real gopher URL like `gopher://host/0/small` sent the
selector `0/small`, and even a correct selector was always fetched as a
menu. Menu-parsing a text file eats the first character of every line as
an item type, so `A short text file.` displayed as `short text file.`
under a `[?]` marker.

`parse_url()` now recognises the type character that a URL carries between
host and selector, and reports it to the caller.

**The awkward part is that the client's own displayed URLs are not in that
form.** The title bar shows `gopher://host:7070//halfline` -- host, `/`,
then a selector that itself begins with `/`. Reading the character after
the first `/` as a type would turn that into type `/` with selector
`halfline`, breaking exactly the URLs users copy back out of the client.

So the type is accepted only when it is a plausible type character **and**
the next character is `/` or end-of-string:

    host/1/foo    type '1', selector "/foo"
    host/0/foo    type '0', selector "/foo"   (text)
    host//foo     no type,  selector "/foo"   (unchanged)
    host/foo      no type,  selector "foo"    (unchanged)

Both entry points handle a text URL by showing it in the pager: the G:URL
key reads it in place, exactly as activating a `[TXT]` item does, with no
history level pushed and no refetch (verified -- the server log shows no
second request when Stop returns to the menu). The start-site chooser does
the same and then asks again, since a text file is not a start site.

## 2.37 Directory chain extension (2026-09-01)

A `.d81` has 8 directory entries in its first block, and `dir_find_slot()`
gave up at the end of the chain, so a disk reported "Directory full" after
8 saved files while ~3000 blocks sat free. It now extends the chain the way
CBM DOS does: allocate a block on the directory track, link the previous
last block to it, initialise it as end-of-chain with all slots empty, and
use its first slot.

Two details worth recording:

- Directory blocks must come from **track 40**, which the ordinary
  allocator deliberately never touches (`bam_find` stops at track 39, so
  file data can never land on the directory track). Hence a separate
  `bam_find_on_track()`. Track 40's BAM entry lives in the first BAM
  sector, already loaded, so no extra sector I/O is needed.
- The new block is fully cleared before use. A recycled sector can still
  hold a previous file's bytes, and a stale non-zero byte at offset 2 of
  any 32-byte slot would read as an occupied entry.

**Verified on hardware** with a crafted disk whose first directory block
was already full (GOPHER, ETHBIN and six padding entries), which tests the
extension with a single save rather than nine:

- Saving `SMALL` succeeded instead of reporting "Directory full".
- On disk: `(40,3)` link became `(40,4)`; the new block ends the chain and
  holds `SMALL`; track 40 shows sector 4 newly allocated; the original
  eight entries are untouched.
- Saving `SMALL` again reported "Already on disk", so the duplicate check
  from 2.33 walks into the extended block.
- Saving `SMALL2` reused slot 1 of the same block -- still two directory
  blocks, still 35 sectors free on track 40 -- so extension happens only
  when genuinely needed.

The disk now holds up to 296 files (37 directory blocks x 8), which is the
1581 limit rather than ours.

## 2.38 Binary downloads (item types 9 and 5) (2026-09-01)

The first v2 feature. Item types `9` and `5` are now selectable, shown as
`[BIN]`, and activating one downloads the file to a mounted `.d81`. The
filename is offered pre-filled from the selector and the drive chooser from
2.30 is reused, so the flow matches saving an article.

**Buffered in attic RAM, not streamed to disk.** The transfer lands at
`$8100000` and is only written out once complete. Streaming straight to the
drive would mean not draining the second stack's receive ring for the duration of
each F011 sector write: the ring fills, the peer's window closes, and
recovery depends on a window update that the second stack has its own history with
(see the local window-update patch). Buffering keeps the
network and disk halves entirely separate, and the attic has room to spare
-- the text store, menu cache and history all sit below `$80a0000`.

**The cap is the allocator, not the disk.** `cbmdos` allocates only on
tracks 1-39, whose BAM lives in a single sector, giving 1560 blocks x 254
bytes = 396,240 bytes. A `.d81` could hold roughly twice that if the second
BAM sector (tracks 41-80) were supported. Exceeding the cap is reported as
"Too large: NNKB exceeds the 387KB a disk can take" rather than truncating
silently.

### Verified on hardware

The test server (`tools/download_test_server.py`) serves a deterministic
payload -- byte `i` is `(i*7 + (i>>8)) & 0xff` -- so the file written to the
disk can be checked against a regenerated copy without transferring a
reference separately. It deliberately contains `$00`, `$0a`, `$0d` and
`$2e`, which proves the binary path does no line-ending or "." terminator
handling.

| size | blocks | result |
|---|---|---|
| 32,768 | 130 | byte-for-byte identical |
| 262,144 | 1033 | byte-for-byte identical |

The 256KB transfer took roughly 110 seconds end to end, about 2.4KB/s.
That is the whole path (network, per-byte `lpoke` into attic, then per-byte
`lpeek` out to the disk writer); which part dominates has not been
measured.

**Not done:** these files are written as SEQ, like saved articles. A
downloaded `.prg` would need PRG type to be `LOAD`able by name, but a
gopher type-9 file is generic binary and guessing wrong is worse than being
consistent -- the first two bytes of a PRG are a load address, so mislabelling
arbitrary data as PRG would make `LOAD` place it anywhere. Offering the
type as a choice is the obvious next step.

## 2.39 Persistent start page; the struct mirror bug (2026-09-01)

Bookmarking works. `M` on a menu saves the current page to `GOPHER.CFG` on
the boot disk; the start chooser offers it as option 4 on the next run.

`gopher_config.c` had been dead code for most of the project: it was
written against the KERNAL disk path, which was made to work in isolation
but destabilised the client, because `$d030` carries VIC-III/IV
configuration as well as ROM banking and switching it fights the
80-column screen. Its own comment predicted the fix -- "a safe
implementation probably has to avoid the KERNAL altogether, driving the
F011 floppy controller directly" -- so it was simply rewired onto
`gopher_cbmdos.c`. No logic changed; only the storage backend.

`cbmdos_delete()` was added for this: `cbmdos_create()` refuses duplicates
(2.33), so rewriting the config means removing it first. It frees the
file's blocks through a new `bam_free()` and clears the directory entry,
with the chain walk bounded so a corrupt or self-referential chain cannot
loop forever. It is a generally useful primitive -- a "delete file" UI
would now be straightforward.

The saved page is **offered**, not applied silently. The `.d81` is also the
distribution medium, so an image shared after bookmarking would otherwise
redirect its recipient with no explanation.

`gopher_kernal.c/h` had no callers left and moved to
`attic/kernal-disk-io/` with a README recording what it proved. The binary
did not shrink -- the linker was already dropping it -- so this is tree
hygiene, not a saving.

### The bug this uncovered

The first successful save wrote `GOPHER1\ngopherpedia.com\n0\n/lang=en\n`.
The port should have been 70.

`gopher_config.c` carried its own copy of `struct location`, introduced
with the comment that it mirrored "just what we need rather than moving
the definition, which would churn the whole client". The copy went stale:
`LOC_SELECTOR_LEN` grew to 80 in `gopher.c`, to hold selector + TAB +
query for type-7 searches, while the mirror stayed at 47.

The two structs then disagreed by 33 bytes, so `port` sat at a different
offset in each. Saving read the port from inside the selector array and
found 0. Loading would have written the port back **into the middle of the
selector** -- corruption across a module boundary. Nothing warned, because
each file compiled against a self-consistent definition, and it stayed
invisible while the feature was disabled.

The definition now lives in `src/gopher_loc.h` and both files include it.
Verified after the fix: `GOPHER1\ngopherpedia.com\n70\n/lang=en\n`.

**Worth generalising:** a duplicated type definition is a latent bug with a
delay fuse. It cannot be caught by the compiler and it only fires when
someone changes the original, which is exactly when nobody is looking at
the copy.

### Verified on hardware

- No config: chooser shows three options.
- `M` on gopherpedia: "Saved as start page".
- After a reset and remount: option 4 reads
  `gopherpedia.com /lang=en  (saved)`, and selecting it navigates there.
- `M` again with the file already present: exactly one `GOPHER.CFG` in the
  directory afterwards, so delete-then-create replaces rather than
  duplicating.

### Test-harness note

`m65 -T` drops the first character or two typed into a freshly opened
prompt. `read_line()` deliberately flushes on entry to discard the
keystroke that opened it, and virtual typing arrives faster than any human
would manage. It made `192.168.1.232` arrive as `92.168.1.232` repeatedly.
Not a client defect, but scripted tests should prefer single-key paths, or
send the text a second time.

## 2.40 Second BAM sector: the whole disk is usable (2026-09-01)

The allocator held only the first BAM sector, so every file was confined to
tracks 1-39 -- about 387KB of a disk that holds nearly 800KB. Irrelevant
for saved articles, and the binding limit for downloads (2.38).

A 1581 splits its BAM across two sectors on the directory track. Layout
confirmed against a real image before touching any code:

- `(40,1)` covers tracks 1-40 and links to `(40,2)`; `(40,2)` covers
  41-80 and ends the chain.
- Entries are 6 bytes per track from offset 16 -- a free count then a
  40-bit map -- at `16+(t-1)*6` in the first sector and `16+(t-41)*6` in
  the second.
- Both carry the same DOS version and disk ID in bytes 2-5.

`bam_load`/`bam_save` now handle both sectors, and `bam_alloc`, `bam_free`
and the free-block search route by track. `bam_find` scans inward from the
directory track (39 down to 1, as CBM DOS does, keeping small files off the
rim) and then outward across the second sector (41 up to 80). **Track 40 is
never handed out for file data** -- it holds the header, both BAM sectors
and the directory chain.

Capacity goes from 1560 blocks (~387KB) to 3160 (~782KB), and
`DOWNLOAD_MAX` rises to match. That is the difference between holding a
`.d64` and holding most `.d81` images.

The second BAM sector lives in `.bss`, not at a fixed low-RAM address like
the first. Those fixed addresses exist because `.bss` was full at the time,
not because they are faster: a `.bss` array's address is just as constant
to the compiler. Since 2.29 freed the space, new buffers belong where the
linker can guarantee they are nobody else's -- which 2.30 showed is not
true of hand-picked addresses.

### Verified on hardware

A 460,800-byte download onto a disk with only ~376KB free below track 40,
so it could not have succeeded without the second sector:

- 1815 blocks, byte-for-byte identical to the served payload.
- Blocks span **37 tracks below 40 and 10 above** -- the boundary is
  genuinely crossed, not merely reachable.
- Track 40 holds no file data.
- Every per-track free count matches its bitmap across all 80 tracks, in
  both sectors. That check matters more than the others: an allocator that
  writes correct data while corrupting the BAM looks fine until the next
  file is written, which is exactly how 2.24 went wrong.

## 2.41 Download file type, and a bookmark list (2026-09-01)

### PRG or SEQ on download

Downloads previously always wrote SEQ. The flow now asks, after the drive:
`File type: P)RG or S)EQ? (Return = SEQ, Stop cancels)`, remembering the
choice like the drive so a run of downloads is not a run of identical
answers.

SEQ stays the default deliberately. A gopher type-9 item is generic
binary, and `LOAD` reads a PRG's first two bytes as its load address -- so
labelling arbitrary data PRG makes `LOAD` scatter it into memory at
whatever address those bytes happen to encode. PRG is correct only when the
file really is a program, which only the user knows.

`cbmdos_create_as()` carries the type; `cbmdos_create()` remains as a
wrapper defaulting to SEQ, so the save and config paths are untouched. The
type byte is written at close, so it is held in a static between the two.

**Verified on hardware:** a 4096-byte download chosen as PRG produced a
directory entry of type `$82` (17 blocks) whose contents were byte-for-byte
identical, alongside `GOPHER.CFG` still at `$81`.

### Bookmarks, not one start page

`GOPHER.CFG` now holds up to `CFG_MAX_BOOKMARKS` (6) entries -- what the
start chooser can list without scrolling -- under a new `GOPHER2` magic.
Files written by the single-page format are still read: both magics parse
identically from the first entry onward, so an older config is not silently
discarded.

**`M` is a toggle.** It bookmarks the page being viewed, or removes it if
already bookmarked, matching on host, port and selector. One key does both,
which avoids needing a separate management screen just to delete an entry.
A list at capacity reports "Bookmark list is full (6)" rather than silently
dropping the oldest.

An empty list removes `GOPHER.CFG` entirely rather than writing an empty
stub, so a disk shared after clearing bookmarks carries none.

The chooser lists them as options 4 upwards and adjusts its prompt --
"Press 1-3, or 4-5 for a bookmark." They remain *offered*, not applied: the
`.d81` is the distribution medium, and an image shared after bookmarking
should not redirect its recipient unexplained.

**Verified on hardware:**

- Add, then `M` again removes ("Bookmark removed: gopherpedia.com"), then
  add again -- the toggle round-trips.
- Removing the only bookmark leaves no `GOPHER.CFG` and the chooser returns
  to three options.
- Two bookmarks from different sites survive a reset and remount, listed as
  options 4 and 5; selecting 5 navigates to floodgap.
- On disk: `GOPHER2` / `gopherpedia.com` / `70` / `/lang=en` /
  `gopher.floodgap.com` / `70` / `` -- ports correct, empty selector
  preserved as an empty line.

### Harness note

Scripted testing leaned entirely on single-key paths this time. `m65 -T`
drops the first characters typed into a freshly opened prompt (2.39), and
waiting on a status-line string is unreliable because the previous screen's
status line is still present while the next page loads. Waiting on the
*title* line changing is the better signal.

## 2.42 Foreground colour reset after every disk write (2026-09-03)

Reported from use: the text colour changed after saving a file. The colour
chosen with F reverted to whatever the machine started with.

`gopher_screen_init()` runs again after every disk write, because the write
tears the 80-column mode down, and it re-read all three colour registers
each time. But conio's `textcolor()` sets only its own internal
`g_curTextColor` -- **it never writes `$0286`** (confirmed in the libc
source). So a foreground chosen with F lived only inside conio, while
`$0286` still held the value the ROM left at boot. Re-reading it snapped
the foreground back to the startup colour.

The asymmetry is the tell, and it matches the report exactly: `bgcolor()`
and `bordercolor()` *do* write `$d021`/`$d020`, so re-reading those
returned the user's actual choice. Only the foreground moved.

`save_article()` made it look handled -- it saved and restored `$d020`,
`$d021` and `$0286` around the write -- but restoring `$0286` restored the
stale value, so it was not merely redundant, it was part of the bug. That
save/restore is gone. The `M` bookmark key and the download path called
`gopher_screen_init()` with no colour handling at all and were affected
identically; all three are fixed by the one change.

**Fix:** read the hardware once, to inherit whatever scheme the ROM left,
then treat this program as the authority and re-apply what it knows.
`apply_colours()` writes `$0286` explicitly so the ROM's notion stays in
step with conio's.

### Verified on hardware, in the reported scenario

Boot colours were border 6, bg 6, text 14. Four presses of F moved text to
2. A real save of a floodgap article -- "Saved to drive 8: PROXY
(27 lines)" -- left border 6, bg 6, **text still 2**, confirmed both by
reading the client's own variables and by a PNG capture showing red text
throughout. Before the fix this reverted to 14.

Also checked against a bookmark write (`M`), which exercises the same
`gopher_screen_init()` path through `cbmdos_delete`.

### Two notes on method

- The client's colour state was read directly from `start_border`,
  `start_bg` and `start_text` (zero-page, `$3a-$3c`) rather than judged
  from screenshots. Comparing PNGs by eye would not have distinguished
  "held" from "reset to a similar colour".
- The first reproduction attempt was wrong: the client was assumed to be
  where it had been left, but it was in the text pager, which handles
  none of the keys sent. Rapid keypresses are also unreliable because the
  menu loop calls `flushkeybuf()` before each `cgetc()`, so keys sent
  faster than the loop turns are discarded. Send one key, then wait for a
  screen read, then send the next.

## 2.43 Start screen: typed selection, delete, and Home (2026-09-03)

Three changes from use, all to the start screen.

**Typed selection instead of a single keypress.** The prompt enumerated the
valid keys -- "Press 1-3, or 4 for a bookmark." -- which is both noisy and
a dead end: a single key cannot address more than nine entries. Selection
is now typed and confirmed with Return, under a fixed prompt:

    Select the number of a bookmark and press Return.

`CFG_MAX_BOOKMARKS` rises from 6 to 12, which is what fits alongside the
three fixed options, the prompt and the input line on a 25-row screen. The
config buffer grows to 2048 bytes to hold 12 entries at their worst case
(host 31 + port 5 + selector 80, each with a newline) -- undersizing it
would have silently truncated the last bookmarks on save.

**Deleting from the screen that lists them.** `D` before a number removes
that bookmark: `D4`. Previously the only way to remove one was to navigate
back to the page and toggle `M`, which is awkward for a bookmark you can
no longer reach. The hint line appears only when there is something to
delete. Typed selection is what made room for this -- there was nowhere to
put a delete gesture in a single-keypress interface.

**Home twice returns here.** Home goes to the start page as before, but
pressing it again when already there reopens the start screen. Without it
the bookmark list was unreachable without restarting the program, and Home
at the start page did nothing at all. Implemented with a `want_chooser`
flag that the menu loop sets and the main loop acts on, since the chooser
has to run outside the inner key loop.

The input row is placed from `wherey()` rather than a constant, because
the list grows and shrinks and a fixed row would either overlap it or
leave a gap.

### Verified on hardware

- Chooser renders the new prompt; the delete hint is absent with no

- Typing `2` + Return reaches gopherpedia.
- `M` bookmarks it; Home from that page returns to the start screen with

## 2.44 $0286 is not the text colour (2026-09-03)

Reported from use: the client sometimes started with light grey text
instead of the MEGA65's white, and only sometimes -- it varied between
runs.

`gopher_screen_init()` inherited the text colour by reading `$0286`, on
the assumption recorded in that file that "the MEGA65 ROM keeps the
current text colour at $0286". **That assumption is wrong.** Measured at
the BASIC 65 prompt: the screen plainly shows white text on blue, while
`$0286` reads 14 (light blue). It held other values at other times
depending on what had run before, which is exactly why the startup colour
varied.

So the client was starting in whatever colour that unrelated byte happened
to hold. The fix is to stop inheriting it: the text colour starts at
`COLOUR_WHITE`, which is what the machine itself displays, with a guard so
it can never equal the background.

Border and background **are** still inherited. The program has never set
them, and `PEEK` from inside the program reads them accurately -- 6 and 6,
blue on blue, matching what the ROM leaves and what the screen shows.

This also corrects the reasoning in 2.42. That fix was right about the
symptom and right about the mechanism -- `textcolor()` never writes
`$0286`, so re-reading it after a disk write discarded the user's choice --
but it repeated the false premise that `$0286` was authoritative, and even
started writing to it to "keep the ROM's notion in step". There is no such
notion to keep in step. All reads and writes of `$0286` are now gone.

**Method note.** `--memsave` reported `$d020` and `$d021` as 0 (black)
while the screen was plainly blue, which is the same I/O-register
unreliability seen with `$d083` (2.25) and `$d7fa` (2.34). `$0286` is
ordinary RAM and read consistently, and the program's own `PEEK` of the
I/O registers is accurate. The discrepancy is only in host-side reads: use
them for RAM, and read I/O from inside the program.

### Verified on hardware

- Startup: `start_text` = 1, and a PNG capture shows bright white on blue,
  matching the BASIC 65 screen beside it.
- Regression on 2.42: `F` twice moves the text colour to 3, a bookmark
  write follows, and it is still 3 afterwards.

## 2.45 Built-in sites become ordinary bookmarks (2026-09-03)

gopherpedia and floodgap were hard-coded options 2 and 3 and could not be
removed. They are ordinary bookmarks now: option 1 stays "Enter a Gopher
site" and bookmarks are numbered from 2, so they can be deleted like any
other.

**Absent config vs empty config.** Seeding defaults when the list is empty
would resurrect them the moment the user deleted them. Those two states
must be distinguishable, so `config_save` no longer removes the file when
the count reaches zero -- it writes a file holding just the magic line, and
`config_load` returns the new `CFG_NO_FILE` only when no file can be read
at all. Absent means "never configured", so the defaults are seeded; empty
means "the user cleared them", which is respected. A file that exists but
is not ours reads as zero entries rather than `CFG_NO_FILE`, so defaults
are never seeded over somebody else's file.

The seeded defaults are deliberately **not** written to disk at startup.
Writing on every first run would touch a disk the user may not want written
to, and it is unnecessary: the file appears the moment they add or remove
anything, and until then re-seeding each run gives the same result.

### A third instance of the llvm-mos miscompilation

This did not work first time. Deleting a bookmark reported nothing but
never reached the disk, and before that the machine hung outright at the
start screen.

Both were the same defect family as 2.34 and 2.42's neighbourhood:

1. **The hang.** `append()` in `gopher_config.c` used
   `strcat(dst, src)`, which compiled to a scan loop whose pointer bytes
   were reloaded each iteration from zero-page locations the loop never
   updated -- so it re-read one byte forever. Found by reading the PC over
   the serial monitor: `$802B`, inside `config_save`. It surfaced only
   when `buf` grew from 1024 to 2048 bytes, which was enough to change
   code generation.

2. **The silent failure.** Rewriting `append()` around a file-scope
   `static unsigned int buflen` did not work either. The appended text
   landed in the right places but the static never advanced past the first
   call, so the closing `buf[len] = 0` wrote its NUL back over the first
   byte of the second field and the caller then wrote only 8 bytes.
   Observed directly in memory: `buf` held `"GOPHER2\n"`, then a NUL where
   `g` should have been, then `"opher.floodgap.com"`, with `buflen` still
   reading 8. Not a zero-page collision -- `buflen` sat cleanly at `$51`
   with `f011_ds` at `$53`.

The write position is now passed in and returned, so it lives in locals
threaded through the calls. **The pattern to avoid is clear enough to state
as a rule: do not accumulate a buffer position in a file-scope variable,
and do not build strings with `strcat`/`strlen` chains. Pass an index and
return it.**

**Known remaining risk:** `ui_set`/`ui_add`/`ui_add_uint` in `gopher.c`
share exactly this shape, accumulating into a file-scope `ui_len`. They
work today and are used everywhere, so they have not been churned -- but if
a status or menu line ever appears truncated, or with its first character
clobbered, this is the first thing to suspect.

### Verified on hardware

- Fresh disk: both defaults seeded as bookmarks 2 and 3.
- `D2` removes gopherpedia; floodgap renumbers to 2.
- Restart: floodgap persists as 2 -- partial state survives.
- Deleting the last one leaves `GOPHER.CFG` containing exactly
  `"GOPHER2\n"`, and after a restart the defaults do **not** return.

### Harness note

Return was the hardest keystroke to deliver. `m65 -t '~M'` is unreliable on
its own, and poking `$d610` through the monitor does not work -- writes to
I/O registers are as unreliable as reads (2.44). What works is putting the
whole line in one `-T` invocation, which appends the Return itself:
`m65 -T ' d2'`. The leading space is deliberate -- a dropped first
character still parses, because the input parser skips spaces.

## 2.48 Real floppies: two bugs fixed, feature disabled (2026-09-03)

Saving to the internal drive is **refused** rather than attempted. Two real
driver bugs were found and fixed on the way, and both are keepers, but
reads from physical media stayed unreliable, so the path is not
trustworthy enough to offer.

### What was fixed

1. **NOBUF (2.47).** The sector buffer pointers were never reset. Proven
   fixed on hardware: `EQ` now sets on completion, which had never once
   happened before, and the drive audibly ran.
2. **The side mapping is inverted between real media and images.** A real
   1581 keeps the directory track's header and BAM on physical **side 1**;
   a mounted `.d81` keeps them on side 0. Surveyed directly: side 0 read
   back as all zeros across all ten sectors, while side 1 sector 1 began
   `$28` -- the link byte pointing at track 40, exactly what the CBM (40,0)
   header contains. Corroborated independently: BASIC reads that same
   sector with `$D080` bit 3 set. `side_for()` now picks the side from the
   drive's own mode, read from `$D68B`.

   This single fact explains the whole history of this bug: every test
   against a `.d81` passed and every test against the floppy failed,
   because the two disagree about which side the data is on.

3. **Reads are retried** (six attempts, waiting for the disk to turn
   between them so a retry does not land on the same spot). One attempt
   per sector is not how a floppy is read.

### Why it is still disabled

Even with all three, reads remain intermittent. The clearest evidence: the
same sector on the same disk, with the drive spinning throughout, read
cleanly with valid data on one survey pass and timed out on the next. That
is characteristic of marginal media or a timing detail still wrong in the
low-level read, and a save that half-works is worse than one that is
declined.

`choose_drive()` therefore refuses any drive that `$D68B` reports as real
media, with "Drive N is a real floppy - only mounted .d81 images are
supported", and re-prompts. Mounted images work on either drive.

### Verified on hardware

- Drive 8 while image-backed: accepted, save proceeds.
- Drive 8 with `D0IMG` cleared: refused with the message, prompt redraws,
  drive 9 then saves normally.
- Drive 9 (image): "Saved to drive 9: PROXY (27 lines)" -- no regression
  from NOBUF, the side mapping or the retries.

### What this cost, and why

This took far longer than it should have, for one reason: **the test
environment kept lying about which device was being addressed.** Every
`m65 -F` reset re-applies the auto-mount, putting an image back on drive 8
and silently undoing a floppy assignment made through the machine's UI.
Two "verifications" were recorded against a mounted image while believing
they were the floppy, and the tell -- the client reporting a file "already
on disk" for a disk stated to be empty -- was rationalised instead of
investigated.

Poking `$D68B` is not a substitute for the UI assignment: the register
changes, but the motor never turns. Only the machine's own assignment
routes to the physical drive. Since a reset destroys it, the working
procedure is: load the build first, have the user assign the drive, then
run without resetting.

**The rule worth keeping: confirm which device a disk test addressed --
by the disk's name -- before believing the result.**

## 2.47 NOBUF: the real cause of the floppy failure (2026-09-03)

**2.46's verification below was invalid and its fix is unproven.** Drive 8
was a mounted disk image throughout that testing -- the old savetest image
named "M65 MENU SYSTEM" -- not the physical drive. Every `m65 -F` reset
re-applies the auto-mount, which puts an image back on drive 8 and undoes
a floppy assignment made through the machine's UI. Confirmed: after a
reset `$D68B` reads `$07` (D0IMG=1, drive 0 served by an image); with the
floppy assigned it reads `$38` (D0IMG=0).

The tell was ignored at the time: the client reported "Already on disk -
PROXY" for a disk the user had just said was empty, and that was
rationalised rather than investigated. **Before claiming a disk test
passed, confirm which device was addressed -- check the disk's name, not
just that the operation returned success.**

### The actual defect

`NOBUF` (bit 0 of `$D081`) is documented as *"Reset the sector buffer
read/write pointers"*. The name suggests "do not use the buffer", which is
presumably why it was never set. Reads issue `$40` and writes `$84`, both
with that bit clear, so the buffer pointers are never reset and stay
wherever the previous operation left them.

A mounted image is unaffected, because the hypervisor fills the buffer
directly -- which is exactly why every test against a `.d81` passed. On
real media the incoming bytes overflow and are dropped. Measured on the
user's floppy, on a disk BASIC lists correctly as "FLOPPY" with 3160
blocks free:

    stb0 = $09   RDREQ clear before the command (no stale flag)
    stb1 = $a9   RDREQ high -- the sector header WAS found
    sta1 = $c0   BUSY|DRQ -- data started arriving
    sta2 = $04   LOST set, DRQ and EQ clear
    BAM_BUF      still all zeros

So the BAM read returned nothing, every track looked full, and the client
reported "Disk full" on an empty disk. Reads are now `$41` and writes
`$85`.

**This is also the true cause of the displaced writes in 2.26**, which
were worked around by switching to the memory-mapped buffer rather than
fixed at source.

### A second, separate defect

The completion check is wrong. The reference states a complete sector is
indicated by BUSY clear **and DRQ and EQ high**; we test only RNF and CRC,
so a transfer that lost its data is accepted as success. That is why the
failure surfaced as garbage rather than an error.

It cannot simply be tightened: a virtualised image completes with
`sta = $44` (DRQ set, EQ **clear**, LOST **set**) and yet delivers correct
data, so requiring EQ or clear-LOST would break the working path. The two
transports report status differently and any check has to accommodate
both. Not yet resolved.

### Status: UNVERIFIED

The NOBUF fix is built and committed but has **not** been confirmed
against real media. Testing it requires loading a new build, loading
requires a reset, and a reset destroys the floppy assignment. At the last
attempt `DIR U8` from BASIC itself hung with the motor running and LOST
set, so the machine was not in a state to test.

## 2.46 Saving to a real floppy drive (2026-09-03)

Reported from use: saving to the internal drive always failed with
"SAVE FAILED", while saving to a mounted `.d81` always worked.

The whole F011 layer was built and tested against mounted images, which
the hypervisor services instantly. Every timeout in it was calibrated for
that, and the assumption is fatal on real media.

**The bound was 60000 poll iterations -- about 12ms at 40MHz.** A floppy
turns at 300rpm, so a sector can take a full **200ms** revolution just to
come under the head, and the head may have to seek across dozens of
tracks first. The controller was being given roughly a sixteenth of one
revolution to find a sector.

### What the reference actually specifies

Checked in the chipset reference before changing anything, since the code
was written from a working-by-experiment position rather than the
documented procedure:

- Motor on (`$60` to `$D080`), SPINUP (`$20` to `$D081`), wait for BUSY to
  clear -- "the drive is now spinning at speed".
- Select the side, load TRACK/SECTOR/SIDE, issue the read (`$40`), wait
  for RDREQ, then for BUSY to clear.
- **Seeking is handled for us.** The 45IO27's track auto-tune reads sector
  headers and steps the head toward the target track, and is *enabled by
  default* (`$D696` bit 7 clear). That is why no explicit step-in/step-out
  is needed, and why the missing piece was time rather than seek commands.

### The fix

Waits are now paced on the frame counter (`$D7FA`) rather than a spin
count, with a 150-frame (~3s) allowance covering spin-up, a full-stroke
auto-tune seek and at least one revolution. A spin cap remains as a
backstop in case `$D7FA` itself stalls, which has bitten this project
before (2.34) -- without it a dead frame counter would hang in the driver.

**Spin-up deliberately keeps the old short bound.** Against a mounted
image BUSY never clears after SPINUP -- measured, `$d082` reads `$b0` --
so a generous wait there would add seconds to every operation on the
common path for no benefit. A real drive still mid-spin-up is covered
anyway, because the read or write that follows waits on RDREQ/WTREQ with
the full allowance.

Writes now also wait for **WTREQ** (`$D083` bit 6), the write-side
counterpart of RDREQ, before waiting for the transfer. That is where the
revolution is spent on real media; the old code went straight to waiting
for BUSY.

**Write protection is now detected** (`$d082` bit 1, PROT) and reported as
"Disk is write protected" rather than a generic failure. It is the one
write error the user can actually act on.

### Verified on hardware, on a real disk

With `gopher.d81` mounted on drive 9 and the internal drive as 8:

- Save to drive 9 still works -- no regression on the virtualised path.
- Save to drive 8 succeeds where it previously always failed.
- Saving the same name to drive 8 again reports "Already on disk", which
  proves the directory was genuinely written to **and read back from** the
  physical disk rather than the call merely returning success.
- A second, differently-named save to drive 8 also succeeds.

### Note

Two test files, PROXY and PROXY2, were left on the physical disk in drive
8 by this testing.

## 4. Target platform & constraints

Based on the MEGA65's real constraints, and directly informed by
the first stack's FETCH.md (the equivalent design notes for Graze, the closest
existing MEGA65 network-client project):

- **CPU/memory**: 40MHz 8-bit CPU, 384KB main RAM addressable via the VIC-IV,
  optional 8MB+ expansion RAM (slower, CPU-only — good for staging downloaded
  data, not code).
- **CC65 code size**: CC65 output only really fits in the first 64KB of
  address space. Graze (a full HTML/H65-rendering browser) has to solve this
  by splitting into a loader + interactive UI module + network module,
  chained via a shared-memory handoff structure. **We're in a meaningfully
  better position**: since the network stack (the second stack) now runs as a
  standalone binary in bank 4, entirely outside our program's own address
  space (see below), our program only has to hold UI/menu logic — no HTML
  parser, no H65 renderer, no linked-in TCP/IP C code. Module-chaining may
  still eventually be needed if the UI logic itself grows past ~50KB, but
  it's no longer a day-one requirement the way it was for Graze.
- **Networking — the second stack, not the first stack** (see §2 decisions table for why): a
  pure 65CE02-assembly TCP/IP stack, `BLOAD`ed (in the shipped product) or
  injected via `m65 -@` (in dev) as a standalone ~22KB binary at physical
  `$42000` (bank 4, offset `$2000`). It's driven entirely through a
  documented jump-table ABI at `$42000+` (init, DHCP, DNS — both blocking
  and non-blocking, TCP connect/send/receive/disconnect, listen/accept) —
  see the table in the second stack's README. A Gopher request/response maps
  naturally onto the TCP calls: connect → send selector string + CRLF →
  poll/receive into a buffer → treat the peer closing the connection as
  end-of-response (gopher has no explicit content-length).
  **Calling convention (validated on real hardware, `src/trampoline.asm` +
  the second stack's trampoline spike)**: the second stack's jump table is designed to be invoked via
  BASIC65's `SYS <address>`, which for any address above `$FFFF` is
  documented (BASIC65 manual, "SYS" command) to transparently perform a
  4510/45GS02 `MAP`-instruction bank-switch, treating the address as a
  linear 24-bit physical address. Calling it from our own machine code (not
  BASIC) means replicating that `MAP` dance by hand:
  - `MAP` takes A/X/Y/Z: `A`=low byte of a 12-bit page offset, `X`=block-
    enable bits (high nibble) + high nibble of the offset (low nibble),
    `Y`/`Z`=the same for the upper `$8000-$FFFF` quadrant (left zero — we
    don't need it, and touching it would banish BASIC/KERNAL ROM and I/O).
    For the second stack's `$42000` base: `LDA #$00 / LDX #$E4 / LDY #$00 / LDZ #$00
    / MAP / EOM` maps CPU `$2000-$7FFF` to physical `$42000-$47FFF`, so a
    jump-table entry at physical `$42000+N` is called via `JSR $2000+N`
    while mapped, then unmapped the same way (all-zero registers) before
    returning.
  - **The trampoline that does this must NOT live in `$2000-$7FFF`** —
    that's exactly the window that gets swapped out during the call, and
    it's also where a CC65 program's own CODE segment lives once it grows
    past ~6KB. Concretely, trying to place it there (e.g. via a custom
    linker segment inside the same `.prg`) silently fails: a C64 PRG is one
    contiguous byte stream from its load address, so a segment targeting an
    address *below* that load address can't actually be placed there — the
    linker just writes it wherever it falls in file order, physically
    landing at the wrong address with no error. (We hit exactly this: it
    landed right after the BASIC stub, so `RUN` executed only the
    misplaced trampoline, which cleanly `RTS`'d back to BASIC without ever
    reaching our real program — silent, not a crash, which made it
    confusing to diagnose.)
  - **Working solution**: assemble the trampoline as its own tiny (~24
    byte) standalone binary with a fixed origin (`* = $0334`, the classic
    free C64 "tape buffer" zone), inject it separately (`m65 -@
    trampoline.bin@334`) alongside the second stack's own `eth.bin@42000`, and call
    it from C via a function-pointer cast to that fixed address:
    `((void(*)(void))0x0334)();`. This mirrors exactly how the second stack's own
    `eth.bin` is loaded — a separate blob at a fixed address, not linked
    into the calling program.
  - Each distinct jump-table entry we need (DHCP start/poll, DNS
    start/poll, TCP connect/send/receive/disconnect, etc.) will need either
    its own small trampoline at a further fixed offset within the `$0334`
    zone (~200 bytes free total), or one parameterized trampoline that
    self-modifies its `JSR` target — not yet designed; the validated piece
    so far is only the single-entry-point, no-argument case (`$42000`
    init).
  - the second stack's own TODO.md explicitly lists "create a C-friendly integration
    layer" as not-yet-done upstream, so this trampoline is work we own, not
    something to eventually delete in favor of an upstream header.
- **Toolchain**: CC65 for our own program (unchanged decision). the second stack
  itself is 65CE02 assembly built with `64tass` (installed via
  `brew install tass64`, invoked as `64tass`), entirely separate from our
  CC65 build.
- **File I/O**: `mega65-libc`'s `fileio.h`/`fcio.h`/`sdcard.h` cover SD card
  access, needed for the shipped product to `BLOAD` the second stack's `eth.bin` and
  the trampoline from the SD card at startup (dev builds instead inject
  both directly via `m65 -@`, see §7); also the natural path for v2
  downloads.

## 5. Functional requirements (v1)

### 5.1 Startup & connection
- FR-1: On launch, prompt for (or accept as a startup parameter) an initial
  gopher URL/selector — host, port (default 70), and selector (default `/`).
- FR-2: Resolve hostname via DNS if given a name rather than an IP.
- FR-3: Open a TCP connection to host:port; show connection status
  (connecting / connected / failed) on screen.
- FR-4: On connection failure or timeout, show a clear error and return to
  the previous menu (or a retry/quit prompt if this is the first connection).

### 5.2 Menu rendering (item type `1`)
- FR-5: Parse gopher menu lines (tab-delimited: display string, selector,
  host, port) per RFC 1436.
- FR-6: Render only recognized/relevant item types meaningfully in v1:
  - `0` text file, `1` submenu — selectable, navigable.
  - `7` search — selectable; prompts for a query and submits
    `selector<TAB>query`, rendering the reply as a menu (see 2.6).
  - `i` informational line — displayed, not selectable.
  - all other types — displayed with a marker indicating "not supported in
    this version" but not selectable, so menus from real-world servers don't
    break navigation even though they mix in types we don't handle yet.
- FR-7: Support menus longer than one screen: scrollable/paginated, with
  clear indication of position (e.g., "line 12 of 40").
- FR-8: Keyboard navigation: up/down (or equivalent) to move selection,
  return/enter to follow the selected link, a dedicated key to go back.

### 5.3 Text file rendering (item type `0`)
- FR-9: Fetch and display plain text files with basic pagination (the
  gopher convention of a line containing only `.` terminates the response
  for text items and must be handled).
- FR-10: Support scrolling through text longer than one screen.
- FR-11: A key to return to the menu the text item was selected from.

### 5.4 Navigation / history
- FR-12: Maintain an in-memory back-stack of visited menus for the current
  session (back navigation only needs to re-request, not cache, prior
  pages — keeps memory pressure low).
- FR-13: A way to jump back to the start/home page.

### 5.5 Error handling
- FR-14: Distinguish and clearly report: DNS failure, connection refused/
  timeout, connection dropped mid-transfer, malformed menu line.
- FR-15: No error condition should hard-crash the program; always return the
  user to a navigable state.
- FR-16: Save the current text item to disk as a CBM SEQ file, with an
  editable filename derived from the selector. Done; see 2.27 and 2.30.
- FR-17: Let the user choose the destination drive among the MEGA65's two
  mounted drives (device 8 / device 9), remembering the last choice.
  Done; see 2.30. The SD card itself is out of scope for v1: reaching it
  means FAT32, and a mounted `.d81` is reached through CBM DOS instead.

## 6. UI/UX requirements

- UX-1: 80-column display throughout.
- UX-2: A persistent status/title line showing at least: current host, and
  connection state.

- Use **Xemu** (MEGA65 emulator) for fast dev-loop iteration.
- Use the real MEGA65 over the JTAG/serial link for hardware validation —
  we already have a working `m65` CLI build
  (mega65-tools' `m65`, built natively for this Apple
  Silicon Mac) that can load and run a `.prg` and grab screenshots
  (`--screenshot`), which is enough to script "load build, drive it, capture
  screen" checks against real hardware without needing M65Connect.
  **Superseded.** This once said to always pass `-4`/`--c64mode`, from when
  the PRG was a CC65 `c64`-target build loading at `$0801`. The client is
  now a native MEGA65 PRG loading at `$2001`, so `-4` is wrong: it boots
  the machine into GO64 mode and the program never draws. Do **not** pass
  `-4`. The current cycle, which also handles the disk the client reads

- **80-column mode — root-caused and working (`src/screen80_test.c`)**.
  The first attempt (`conioinit()` + `setscreensize(80,25)` + `clrscr()` +
  `textcolor()` + a couple of 80-char `printf()` lines) locked up the
  whole MEGA65 so completely that even `m65 -F` (a hardware-level reset,
  which normally recovers from *any* program-level crash — see the
  ML-monitor case above) stopped responding, for both that program and a
  fresh screenshot attempt; only a physical power cycle recovered it.
  Retesting the exact same sequence incrementally afterward did **not**
  reproduce the hang, but did surface the real, deterministic bug that
  most plausibly explains it:
  - **Root cause**: default C64 screen RAM (`$0400`, 1000 bytes) is too
    small for an 80×25 screen (2000 bytes needed). `mega65-libc`'s
    `clrscr()`/`cputs()` correctly size their writes off the *requested*
    80×25 dimensions, but nothing relocates the screen RAM *base address*
    first — so the extra ~1000 bytes silently overlap our own running
    program's code at `$0801+`. This produced visible on-screen
    corruption (garbage repeated characters) in every retest, and is a
    fully plausible explanation for the original hang too: overlapping
    writes were most likely self-modifying the very program that was
    running, which can do arbitrarily bad things depending on exactly
    what got overwritten — plausibly bad enough to wedge the JTAG/serial
    monitor along with it. **Fix**: call `setscreenaddr(0x50000UL)`
    (mega65-libc's own header docs show this exact relocation pattern)
    before `setscreensize()`. Picked bank 5 specifically to avoid bank 1
    ($10000-$1ffff), since the second stack's DNS lookup needs bank-1 offset
    `$2000-$f7ff` as scratch (see `gopher_net.c`) — using the same region
    for both would work most of the time (DNS staging is brief) but isn't
    worth the risk of a visible glitch or corruption during a lookup.
  - **Second bug, cosmetic but real**: even with screen RAM correctly
    relocated and sized, text still visually wrapped at 40 columns, not
    80. Cause: `conioinit()` calls `sethotregs(0)`, which disables the
    VIC-IV's automatic recalculation of the row-width registers
    (`$D058`/`$D059`, `$D05E`) whenever `$D031` (the H640/80-column flag)
    is touched — a MEGA65 hardware behavior documented in the chipset
    reference's "hot registers" section. `setscreensize(80,25)` only
    flips the `$D031` flag; with hot-regs disabled, nothing else updates
    those row-width registers, so the display stays in wide-pixel mode
    while still logically laid out for 40 characters per row. **Fix**:
    manually `POKE` `$D058`/`$D059`=80/0 and `$D05E`=80 right after
    `setscreensize(80,25)`.
  - **Third finding, an API trap**: CC65's own `stdio.h` `printf()`/
    `puts()` and mega65-libc's `conio.h` `cputc()`/`cputs()` maintain
    independent, conflicting cursor-tracking state — mixing them (as the
    original crashing test did) produces interleaved, corrupted-looking
    text, not a clean failure. **Rule for all future code**: once
    `conioinit()` has run, never call stdio's `printf()`/`puts()` again.
    Separately, `cputs()` itself does *not* interpret `\n` (or any of the
    `{escape}` codes) — only `_cprintf()`/the `cprintf()` macro does that
    parsing (see `conio.c`). So the working pattern throughout the real
    client is: build any dynamic text with `sprintf()` (a pure buffer
    operation, no screen I/O, so it's unaffected by any of the above) into
    a local buffer, then display it with `cprintf()` (cast to
    `const unsigned char *`), never `cputs()` for anything containing a
    newline and never `printf()`/`puts()` at all. Note `cprintf`'s macro
    (`#define cprintf(s) _cprintf(0, s)`) takes a single pre-formatted
    string, not `printf`-style varargs — the `sprintf()` step is what
    supplies the substitution. Also note `_cprintf`'s `{escape}` parsing
    means literal `{`/`}` in untrusted content (e.g. a gopher server's
    menu text) needs sanitizing before display, or it'll be misparsed as
    an escape code — not yet handled, worth a FR when menu rendering is
    built.
  - Confirmed working end-to-end together: `setscreenaddr(0x50000UL)` →
    `setscreensize(80,25)` → the `$D058`/`$D059`/`$D05E` pokes →
    `textcolor()` → `clrscr()` → `sprintf()`+`cprintf()` for all output —
    produces clean, correct, full-width 80-column text with proper line
    wrapping, verified via hardware screenshot.
- **Primary test fixture: `gopher.floodgap.com`** (port 70) — long-lived,
  reliably-up public gopher server, good default target for spikes and
  ongoing manual testing. (Already used to fetch a real menu over the first stack's TCP
  in the phase-1 spike, before the switch to the second stack — see R-1 history.)
- Consider a minimal local gopher server (many trivial ~20-line Python
  implementations exist) for offline/repeatable testing of edge cases
  (huge menus, malformed lines, slow/dropped connections) that
  floodgap won't reliably exercise on demand.
- **Dev-time hardware workflow for the second stack**: build `eth.bin` with
  `64tass src/eth.asm --nostart -o target/eth.bin` (in the `the second stack` repo),
  and the trampoline with `64tass src/trampoline.asm --nostart -o
  bin/trampoline.bin` (in this repo). Inject both, then load/run our
  program, as **three separate `m65` invocations** — combining them (e.g.
  `m65 -F -4 -@ eth.bin@42000 -r prog.prg`) was observed to hang
  indefinitely inside `return_from_hypervisor_mode()` after a successful
  injection; splitting into `m65 -F -4`, then `m65 -@ eth.bin@42000`, then
  `m65 -@ trampoline.bin@334`, then `m65 -r prog.prg` works reliably and

- **R-1 — Networking stack maturity — RESOLVED by switching stacks**:
  the first stack's own upstream README calls it "work in progress, and not yet
  usable." The phase-1 spike (`src/spike.c`, since superseded) confirmed
  DHCP and TCP worked end-to-end against `gopher.floodgap.com` — a real

  layer, we switched to **the second stack**. **Status now**: DHCP and TCP are
  fully validated end-to-end on real hardware through the second stack

  under 1.5s), and (after the R-1c workaround) a full TCP
  session against `gopher.floodgap.com:70` completes: connect, send a

  detect the peer closing the connection (`PUMP` returning nonzero, per
  `TCP_STATE_CLOSED` in the second stack's own poll logic) — all through our own
  general-purpose trampoline (R-1b, now resolved), including calls that
  pass real input arguments (`SET_REMOTEIP`, `SET_REMOTEPORT`) for the
  first time, not just the no-argument case. **This is strictly better
  than where the first stack got us**: the first stack never got TCP-with-DNS working either,
  and the second stack's DHCP+TCP+DNS path (with the R-1c workaround) is now
  proven solid end-to-end.
- **R-1b — Trampoline coverage — RESOLVED**: `src/trampoline.asm` is now a
  general-purpose far-call trampoline (not just the single fixed no-arg
  call from the first validation step). It stages `(target address, A, X,
  Y, Z)` into fixed memory, calls a no-argument entry point, and the
  caller reads `(result A, X, Y, Z)` back from another fixed memory area
  — mirroring the second stack's own internal "ML staged dispatcher" pattern
  (`$4761b`, "args staged at bank-4 $77c0"). C-side wrapper:
  `src/the far-call header`'s `the far call(addr, a, x, y, z)`. Validated against
  real argument-passing calls (DHCP start/poll, TCP connect/send/receive/
  disconnect, `SET_REMOTEIP`/`SET_REMOTEPORT`) and RREG-style multi-byte
  return values (`GET_LOCALIP` etc. returning 4 IP octets in A/X/Y/Z).
  Still open: calls needing more than 4 bytes of input/output (none
  needed yet — the second stack's IP/port-setting calls all fit in A/X/Y/Z).
- **R-1c — the second stack DNS bug — ROOT-CAUSED, WORKED AROUND**: DNS lookups
  through the second stack's jump table reliably stayed in `DNS_STATE_WAIT` forever,
  against both the DHCP-provided DNS server and a hardcoded `8.8.8.8`
  (ruling out a router-proxy-specific issue) — while DHCP (also UDP) and
  TCP-to-an-off-subnet-host-through-the-same-gateway both worked fine.
  **Root cause, found via direct hardware instrumentation** (reading
  the second stack's internal state bytes with `lpeek()` at their physical bank-4
  addresses while polling — see the DNS debug spike in the attic, addresses
  derived from `64tass -l` label export): the second stack's DNS retry/timeout
  pacing (`DNS_TICK`/`DNS_FRAME_TICK` in `src/dns.asm`) detects elapsed
  time by watching the classic VIC-II raster-position registers
  (`$D011`/`$D012`) for a wraparound. On this hardware, those reads —
  **both the second stack's own and our independent direct `PEEK`, taken outside
  any mapped window** — never change across hundreds of real frames (each
  individually frozen at a different static value), even though real time
  is demonstrably passing (confirmed via the MEGA65-specific `$D7FA` frame
  counter, which does advance normally and is what ARP's own retry tick
  and our own polling loops rely on instead). Consequence: DNS's very
  first query send happens synchronously inside `DNS_RESOLVE_START`,
  before ARP has had any chance to resolve the DNS server's MAC — that
  first send fails silently ("ARP not ready"), and because the
  retry-scheduling tick never fires, no resend (or eventual give-up into
  `DNS_STATE_FAIL`) ever happens; it just hangs in `WAIT` indefinitely.
  DNS *response processing*, in contrast, is driven directly by the
  packet-receive dispatch path (`ETH_RCV`, run every `PUMP` call) and
  doesn't depend on the broken tick at all.
  **Working fix (client-side, no upstream change needed)**: fire one
  throwaway `DNS_START` call first purely to trigger ARP resolution for
  the DNS server, wait ~40 frames using our own reliable `$D7FA`-based
  pacing, then call `DNS_START` again — by then ARP is cached, so the
  second call's synchronous first-send succeeds immediately, and because
  response processing doesn't need the broken tick, the reply is handled
  normally and `DNS_STATE` correctly reaches `DONE`. Validated end-to-end
  on real hardware: `gopher.floodgap.com` resolved via the second stack's real DNS
  path, then a full TCP session fetched floodgap's real menu (see
  the second stack's test spike). Still worth reporting the underlying raster-
  read bug upstream (a real fix there would remove the need for the
  double-call workaround and the ~40-frame delay it costs on every
  lookup), but it's no longer a blocker.

- **R-3 — CC65 module-chaining overhead**: following Graze's multi-module

- **R-4 — Scarcity of live gopher servers**: limits how much real-world

- **R-5 — CC65 char-literal comparisons don't match raw ASCII bytes —
  ROOT-CAUSED, FIXED (critical, codebase-wide gotcha)**: while building
  the menu renderer (`src/gopher.c`), server-supplied text displayed as
  dense, chaotic-looking noise even after fixing screen RAM placement,
  the row-width registers, and the printf/cputs conflict (all §7). Root
  cause, isolated via `src/render_test.c` (a standalone test with zero
  networking, using explicit numeric byte arrays — not string literals —
  as input so the test data's ASCII-ness was beyond doubt): **CC65
  translates `char` *literals* via its compile-time charmap**, including
  inside comparisons like `if (c >= 'A' ...)` and switch/case labels like
  `case 'i':`. A `switch` dispatching on a genuine raw ASCII `0x69` ('i')
  byte fell through to `default` instead of matching `case 'i':` —
  proving the compiled value of the literal `'i'` is *not* 0x69 in this
  toolchain/target. This is on top of the already-known fact that string
  literals get this same translation (that's *why* our own hardcoded UI
  text like `"MEGA65 Gopher Client"` displays correctly without any
  runtime translation — it was already translated at compile time). The
  gotcha is that this applies to *every* `char` literal, not just ones
  obviously meant for display — including ones used purely for
  comparison/control-flow against bytes that actually came from the
  network at runtime.
  **Rule going forward, codebase-wide**: any comparison of a
  runtime/network byte against what would naturally be written as a char
  literal (`'0'`, `'i'`, `'\t'`, `'.'`, `'{'`, `'A'`-`'Z'` range checks,
  etc.) must use the numeric ASCII constant instead (`0x69` /* 'i' */),
  with a comment noting the intended character for readability. Control-
  character escapes (`'\r'`, `'\n'`) appear to be an exception — CC65's
  charmap only diverges from ASCII in the printable range, and
  `gopher_net.c`'s outbound `'\r'`/`'\n'` literals are confirmed working
  correctly end-to-end against a real server — but given how easy this bug
  is to reintroduce, treat any *new* char-literal comparison against a
  possibly-network-sourced byte with suspicion and prefer the numeric
  form.
  Applied throughout `render_line()` in `src/gopher.c` (the type-dispatch
  switch, the `.` terminator check, the `\t` field-separator scan, and
  the `{` escape-neutralization). `ascii_to_screencode()` (the case-
  mapping fix from the same debugging session — mega65-libc's
  `petsciitoscreencode()` assumes the wrong charset convention for the
  lowercase charset `conioinit()` selects) also uses numeric bounds for
  the same reason.
- **R-6 — Dropped 'i'/'m' characters — ROOT-CAUSED AND FIXED**: what first
  looked like characters vanishing at the 80-column wrap boundary
  ("community" → "co" + wrap + "unty", "with" → "wth", "running" →
  "runnng") turned out to have nothing to do with wrapping at all.
  Isolated with a minimal, unambiguous test (`src/cprintf_bytes_test.c`):
  feed `cprintf()` a buffer of screen codes 1-26 (lowercase a-z under the
  lowercase charset) and compare against the same bytes via a direct
  `cputc()` loop. The `cputc()` control showed all 26 letters correctly;
  `cprintf()` was missing exactly 'i' and 'm' — nothing else. Root cause:
  `_cprintf()` (`conio.c`) special-cases byte value 9 (`'\t'`, a no-op) and
  byte value 13 as control codes and swallows them with no character
  output. Value 13 is a "control code" here because CC65 compiles the
  escape sequence `'\n'` to PETSCII's own carriage-return convention (13),
  not Unix LF (10) — and 9 and 13 are exactly the screen codes
  `ascii_to_screencode()` (R-5) produces for lowercase 'i' (the 9th
  letter) and 'm' (the 13th letter). Every 'i' and every 'm' in
  server-supplied text was being silently eaten by `cprintf()`'s own
  control-code handling.
  **Fix**: stopped using `cprintf()`/`_cprintf()` for text output
  entirely (both dynamic server text and our own UI strings, for
  consistency and to remove the whole class of risk) in favor of
  `cputs()`/`cputsxy()`, which do a plain `lcopy()` memory copy with no
  character-by-character switch and are immune to this collision.
  Line breaks, previously embedded as `'\n'` inside the strings passed to
  `cprintf()`, are now explicit: a `newline()` helper (`gotoxy(0, wherey()
  + 1)`) called after `cputs()` wherever a line break is needed. Verified
  fixed end-to-end against floodgap's real response: "community",
  "system", "with", "IBM", and "running" all render complete and
  correctly now.
- **R-7 — Screen RAM physically overlapped the second stack's own TCP receive ring
  buffer — ROOT-CAUSED AND FIXED (critical, was corrupting live network
  data)**: after fixing R-6, one small artifact remained — the last info
  line before disconnect appeared truncated and overlapping with a
  repeated fragment ("...your questions and suggestion" immediately
  followed by "Floodgap ha" with no line break). Investigated by capturing
  the *raw* received bytes into a separate memory region as they arrived
  (`src/raw_capture_test.c`, unaffected by any rendering code) and
  dumping them after disconnect. Finding: the captured data itself was
  corrupt — long runs of a single repeated byte in place of real gopher
  content, starting from the very first captured byte, i.e. this had
  nothing to do with rendering or line-wrapping at all. Root cause:
  `gopher_screen_init()` had put screen RAM at physical `$50000` — and
  the second stack's own TCP receive ring buffer lives at exactly `$50000-$50fff`
  (`RING_BUFFER_BANK=$05`, `RING_BUFFER_BASE=$0000`, 4KB —
  the second stack's source). Every character our program drew on screen was
  overwriting the second stack's *live* receive buffer mid-transfer, and the second stack's
  own writes were simultaneously corrupting whatever we'd just drawn —
  explaining essentially every rendering artifact chased this session,
  including the original "wrap boundary" symptom misattributed to R-6 (R-6
  was real and independently worth fixing, but this collision was
  compounding it).
  First fix attempt — bank 6 (`$60000`) — made things *worse* (the entire
  screen showed corrupted content, including our own startup text that's
  drawn before any networking happens at all). Isolated with a
  networking-free readback test (write known bytes, read them back
  immediately): writes to bank 6 don't stick. Root cause: MEGA65's
  standard chip RAM is 384KB, i.e. only banks 0-5 (`$00000-$5ffff`)
  physically exist on typical hardware — bank 6 was never valid memory to
  begin with, not occupied by anything, just absent.
  **Actual fix**: stayed within bank 5 (confirmed working, populated RAM)
  but moved off the second stack's specific 4KB footprint — `setscreenaddr(0x51000UL)`,
  i.e. bank 5 offset `$1000`, leaving `$50000-$50fff` alone. The other
  ~60KB of bank 5 is free. Verified end-to-end against floodgap's live
  response: completely clean now — every line intact, correct case, no
  overlap, no dropped characters, no truncation, clean disconnect.
  **Lesson for any future memory-region choice in this codebase**: don't
  assume a bank is free without checking the second stack's own source for hardcoded
  bank usage (`grep` for `_BANK\s*=` and similar in the second stack's source),
  and don't assume a bank number being "next" or "unused elsewhere in our
  own code" means it's populated hardware at all — verify with an isolated
  readback test before relying on it. Current known allocation: bank 1
  offset `$2000-$f7ff` = the second stack DNS scratch; bank 4 = the second stack code
  (`EXEC_BANK`); bank 5 offset `$0000-$0fff` = the second stack RX ring buffer;
  bank 5 offset `$1000+` = our screen RAM; banks 6+ = not valid memory on
  this hardware.
- **R-8 — TCP receive truncated at ~592 bytes — ROOT-CAUSED AND FIXED**.
  Symptom: any response longer than a few hundred bytes was silently cut
  off (floodgap 592 of 5639), so real menus arrived with no selectable
  links. **The cause was our own code, not the second stack's receive path**:
  `gopher_tcp_send_selector()` sent the request via
  the stack's SEND_BYTE call one byte at a time, emitting a separate
  1-byte TCP segment per character. That tripped a genuine the second stack
  sequencing bug — consecutive small sends go out with wrong sequence
  numbers — and internet servers responded by **RSTing the connection**.
  **Fix**: stage the whole request in `TCP_DATA_PAYLOAD` /
  `TCP_DATA_PAYLOAD_SIZE` and send it once via jump-table entry 8
  (`$42018` = CPU `$2018` while mapped). One segment, no RST.
  **How it was found** (the useful part for next time): four hypotheses
  were killed by measurement before the real one surfaced.
  1. *Drain rate / 45E100 RX FIFO overrun* — killed by
     `attic/cc65-diagnostics/drain_rate_test.c`: 60000 tight-loop polls (vs once per video
     frame) still yielded exactly 592 bytes.
  2. *Receive window backpressure* — killed by `attic/cc65-diagnostics/window_debug.c`:
     advertised window was wide open at 1024, ring buffer fully drained
     (free=4095), `ACK_REPLY_PENDING=0`. No backpressure at all.
  3. *Window-update deadlock* — killed by `attic/cc65-diagnostics/winupdate_probe.c`: at the
     stall `TCP_STATE` was already **0 (CLOSED)**, so nothing could be
     stuck waiting; forcing updates changed nothing.
  4. *the second stack cannot do bulk receive* — killed by running an instrumented
     server on the Mac (`tools/test_gopher_server.py`, same LAN, so both
     ends observable without root/tcpdump): 5635 bytes transferred
     perfectly. Bulk receive was never the problem.
  The decisive instrument was `attic/cc65-diagnostics/teardown_probe.c`, which sampled
  `ETH_RX_TCP_FLAGS` *before* each pump (the pump clears
  `TCP_EVENT_FLAG`, destroying the evidence) and caught `0x04 = RST`
  arriving from the peer at exactly the 592-byte cutoff. The local server
  had already hinted at it: our two terminator bytes arrived **reordered**
  as `\n` then `\r`, which is impossible in a healthy TCP stream.
  **Verified after the fix** (response sizes measured independently with
  `nc`): quux 985 -> **1759 complete**; gopherpedia 1024 -> **3501
  complete** (~50 frames, about 1 second); local control 5635 complete;
  no RST observed, connections end normally in CLOSE_WAIT. The real
  client now parses **56 items** from gopherpedia's root menu with real
  selectable `[DIR]`/`[TXT]` links, and follow-link navigation works.
- **R-8b — no TCP window update ever sent — FIXED LOCALLY in the second stack**
  (the local window-update patch). A second, independent
  the second stack defect, exposed once R-8's RST issue was gone.
  **Cause**: `ETH_MAYBE_WINUPDATE` decides whether to send an update by
  comparing the advertised window as a *size*. That size is clamped to
  `TCP_RECV_WINDOW_CAP` (1024) and `ADV_WINDOW_LAST` holds the same
  clamped value, so the growth test is permanently `1024 > 1024` = false
  and no standalone update is ever emitted. Measured live: `adv=1024`,
  ring free `4095`, `ACK_REPLY_PENDING=0`, peer stalled forever. It is
  masked on most transfers because continuously arriving segments trigger
  ACKs through the normal receive path; it only bites when a peer fills
  the window and then waits — exactly sdf.org's pattern (1024 of 1338).
  **Fix**: we build `eth.bin` ourselves from the sibling `the second stack`
  checkout, so this is patched properly in assembly rather than worked
  around from C. What the peer needs to learn about is the window's
  *right edge*, which advances as the app drains the ring; the size
  cannot grow once pinned at the clamp. The ring `TAIL` advancing is that
  signal, so the patch adds `ADV_TAIL_LO/HI` (global labels — 64tass
  scopes `_name` to the enclosing label, and the two update sites are in
  different scopes), records the tail wherever `ADV_WINDOW_LAST` is
  recorded, and sends an update once the tail has moved `WINUPDATE_GROW`
  (128) bytes since the last advertisement.
  **Explicitly rejected alternative**: zeroing `ADV_WINDOW_LAST` from C
  to force the update branch. It did fire updates, but produced visible
  memory corruption (gopher payload text appearing in unrelated screen
  memory) — reaching into the second stack's live TCP state from the application
  is not safe. That attempt is recorded here so nobody retries it.
  **Verified**: sdf.org 1024 -> **1338 complete** (49 frames, ~1s), with
  no regression on quux (1759), gopherpedia (3584), or the local control
  (5635).
  **Address impact** (important when re-applying): the patch adds 59
  bytes and shifts labels *above* the insertion point. Everything the
  client depends on (`TCP_DATA_PAYLOAD` `$311b`,
  `TCP_DATA_PAYLOAD_SIZE` `$30f7`) is below it and unchanged;
  `TCP_EVENT_FLAG` moved `$4a19` -> `$4a25` and the diagnostics in `src/`
  were updated. Always regenerate `target/eth.labels` after re-applying
  and re-check hardcoded bank-4 addresses. See `patches/LLM-README.md`.
- **R-8c — gopher.floodgap.com is rate-limiting us (open, external)**:
  after many connections during R-8 debugging, floodgap began refusing
  connections outright and now delivers only partial responses slowly
  (1128 of 5639) while the connection stays ESTABLISHED with no RST —
  i.e. throttling, not a protocol stall. Their own root menu warns about
  bot blocking and asks clients not to cost them bandwidth. **Use
  gopherpedia.com or the local test server
  (`tools/test_gopher_server.py`) as the default development target**,
  and treat floodgap as an occasional spot-check only. Not a client bug.

## 9. Suggested phasing

1. **Spike (the first stack)** — done, superseded: `src/spike.c` proved TCP/DHCP work
   but DNS doesn't (R-1 history).
2. **Trampoline validation (the second stack)** — done: `src/trampoline.asm` is now
   a general-purpose trampoline (args + return values), validated against
   real calls including argument-passing ones (R-1b resolved).
3. **Spike (the second stack)** — done, fully: the second stack's test spike proves
   DHCP, DNS (via the ARP-pre-warm workaround, R-1c), and TCP end-to-end —
   resolves `gopher.floodgap.com` by name, connects, sends a selector, and
   receives floodgap's real response, with clean disconnect detection.
   FR-1/FR-2 (§5.1) can now be implemented as originally written (hostname
   resolution works); the DNS workaround just needs to become a real
   function in the client's networking module (currently inline in the
   spike) and costs ~40 extra frames (<1s) per lookup.
4. **Menu parsing + flat rendering** — done, cleanly: `src/gopher.c`
   fetches the real root menu from `gopher.floodgap.com`, parses
   tab-delimited RFC 1436 lines as they stream in, and renders each with a
   type marker (`[DIR]`/`[TXT]`/`[QRY]`/`[URL]`/blank-for-info/`[?]`),
   confirmed against live data end-to-end on real hardware — every line
   intact, correctly cased, no dropped characters, no overlap, clean
   disconnect. Getting here required root-causing and fixing six separate,
   non-obvious 80-column/CC65/the second stack issues (all §7/§8: screen RAM
   placement, row-width registers, the printf/cputs conflict, R-5's
   char-literal gotcha, R-6's cprintf()-swallows-'i'/'m' bug, and R-7's
   screen-RAM/ring-buffer physical memory collision — R-7 in particular
   was corrupting live network data, not just display, and explains most
   of the artifacts chased under R-6's name before R-7 was found). Modules:
   `src/gopher_screen.c` (80-column setup),
   `src/gopher_net.c` (networking, extracted from the spike), `src/gopher.c`
   (parsing/rendering/main).
5. **Navigation** — done: selection, follow-link, and back/home work
   against real menus. Required fixing R-8 (requests were being sent one
   TCP segment per byte, which made servers RST us and truncated every
   real menu to its first few hundred bytes) and a stack-smashing bug
   where `find_next/prev_selectable()` passed 1-byte buffers to
   `item_get()`, which writes up to 72. Menu items live in banked memory
   (`src/gopher_items.c`, bank 5 offset $2000) rather than the 64KB CPU
   window. Known remaining limitation: sdf.org-style servers cap at 1024
   bytes (R-8b) -- since fixed by a local the second stack patch.
6. **Text file viewing** with scrolling.
7. **Polish**: error handling (FR-14/15), pagination, status line.
8. **Module split** (if forced by code size — see R-3, now lower-priority
   since the second stack no longer counts against our program's own code budget):
   break UI logic into a loader/UI/whatever split, once the single-file
   version is working and its real size is known.
